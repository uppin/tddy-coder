# Changesets Applied

Wrapped changeset history for tddy-vm.

- **2026-08-14** [Fix] **image chaining that actually chains — implicit qcow2 flattening removed from every production path** — `cloud_init.rs` copied its source image into a scratch subdirectory and ran `base_convert_argv` (`qemu-img convert -f qcow2 -O qcow2`) on it, a function whose own doc comment advertised that it *"flattens any prior backing chain on the source into a standalone, immutable base image"*. Every bake therefore produced a full standalone copy plus a delta, so a three-layer "chain" cost three copies of everything beneath it — and because `fs::copy` moves only the overlay file, chaining a layer onto an already-prepared base stranded that base's deliberately **relative** backing reference one directory deeper and died with *Could not open backing file*. Now the imported pristine image is the **only full image in the system**: `base_convert_argv`, `copy_and_convert_base`, `promote_prepared_base_pair` and `move_scratch_output` are deleted, `CloudInitLibraryPaths` loses `prepared_base_output`, and `build_cloud_init_image` chains a delta directly onto whatever image it is given — pristine import or provisioned layer alike — via the new pure `relative_backing_path` (bare basename for a sibling, `../01-base/x.qcow2` across tiers; returns `Result` and refuses a mixed absolute/relative pair rather than emitting a walk that resolves to nothing). Because qcow2 resolves a relative backing path against **the directory holding the referencing image**, not the process CWD, the overlay is created at its final path and never moved, and `run_qemu_img` gained a `cwd` so `create -b <relative>` validates the parent from the right directory. Three defects found by validation, each pinned by a test watched failing first: the overlay is created where the previous bake left a **sealed `0444`** file, and `qemu-img create` opens `O_WRONLY|O_CREAT|O_TRUNC`, so the *second* `tddy-vm-build cloud-init --name X` and every re-issue of `BuildTddyHostImage` died `EACCES` — `unseal_existing_overlay` mirrors `import_base_image`'s unlock-before-overwrite; a **relative** library root made both the output and the backing check resolve under the new cwd, so `tddy-vm-build cloud-init` with no `--library-root` failed 100% of the time (`default_tddy_data_dir()` is the relative `tmp/.tddy` in debug builds) — both paths are canonicalized now; and `create_vm` generated a per-VM keypair that **nothing ever injected into the guest**, so with `BatchMode=yes` + `IdentitiesOnly=yes` every `ssh`/`scp` into a library VM had no way to authenticate — it now writes a per-VM NoCloud seed authorizing that key, attached at both boot sites. `import_base_image` rejects a chained source (reading the qcow2 header's `backing_file_offset` directly) instead of silently stranding it. `qemu.rs` also gains `scp_opts`/`scp_to_guest_argv`/`scp_to_guest`, factored with `ssh_opts` through a shared `client_opts` — separate functions because `scp` spells the port `-P` and reads `-p` as *preserve modification times*, which would leave the port number in the argv as another source path. Guarded by `no_disk_flattening_acceptance.rs`, which scans production sources for a qcow2-source convert and allowlists only the two legitimate raw-to-qcow2 normalisers (`build.rs`, `tddy-build-qemu`). Tests: 208 across `tddy-vm`/`tddy-vm-build`/`tddy-vm-testkit`, 0 failed; `clippy -D warnings` clean. **Not closed and flagged in `docs/dev/TODO.md`:** `VmManager::start` still boots with `seed_iso: None`, so a library VM started through the *daemon* has the same authentication gap; and no layer records its parent's identity, so a re-imported base silently changes the bytes under every child. Feature [vm/tddy-vm.md](../../../docs/ft/vm/tddy-vm.md); cross-package [changesets.md](../../../docs/dev/changesets.md). (tddy-vm, tddy-vm-build, tddy-vm-testkit, tddy-e2e)
- **2026-08-02** [Feature] **Daemon-spawned tddy host VM — `BuildTddyHostImage` + `CreateVmFromPreparedBase`, and the launcher corrections they stand on** — the crate could not boot a guest on an Apple Silicon host at all: `QemuVmArgs::build` hard-coded `qemu-system-x86_64`, `-m 512M`, no `-smp`, no accelerator and no firmware, so `RunPolicy`'s persisted memory/cpus were ignored and the aarch64 `virt` machine (which has no BIOS) had nothing to boot through. `vm.rs` gains `VmArch`/`VmAccel` (with explicit `host()`/`host_default()` constructors — the launcher itself never guesses), `UefiFirmware`, `VmLogin`; `qemu.rs` gains `qemu_binary`, `machine_arg`/`cpu_arg` (`-cpu host` under HVF/KVM, `cortex-a72`/`max` under TCG), a two-`pflash` UEFI pair, `-cdrom`, virtio-9p `-fsdev`/`-device`, `resolve_uefi_code_path` (env `TDDY_VM_UEFI_CODE`, else derived from the emulator's own installation — **an unresolvable image is an error, never a silent BIOS fallback**), `ensure_uefi_vars_file` (64 MiB, idempotent), a shared `spawn_emulator`, and SSH as `LoginPolicy.username` with `-i <key>`/`IdentitiesOnly=yes` in place of unconditional `root@` + the ambient agent key. New `serial_shell.rs`: a UART driver ported from `~/Code/makers-lt`'s `@wix/shell-utils` but restructured so the parsing core is **pure** (`SerialShell::feed` returns events; 21 unit tests, no VM) — a shell prompt is believed only *after* a login/password prompt, because cloud-init frames its host-key banner in rows of `#` and mistaking one for a prompt makes the driver type commands at a getty; command completion comes from a per-command exit-code marker, not a prompt regex, so output containing prompt- or login-shaped lines is harmless. New `tddy_host.rs`: the cloud-init recipe (9p mount → rsync → Nix → `./release` → `bun run build` → `./install --systemd`) plus `build_tddy_host_image`, and `ninep_capable_kernel_command` — Debian's *cloud* kernel ships **no 9p modules at all**, and installing the generic flavour is not enough because GRUB keeps preferring cloud, so the step also purges it, `update-grub`s and reboots, guarded on `uname -r` to bound it to one reboot. `cloud_init.rs` gains `NinePShare`, `owner`/`defer` and `plain_text_passwd`/`lock_passwd` on its document types, `render_user_data_without_completion` (a long-lived guest must not inherit the bake's self-halt), `promote_prepared_base_pair`, and **drops `-no-reboot`** so a mid-bake guest reset restarts the guest instead of ending the emulator. `library.rs` generates the per-VM ed25519 keypair `create_vm` had always documented but never written. `registry.rs`: `run_manifest_for` propagates instead of silently substituting a root/no-key/host-arch manifest, `start` resolves firmware *before* the `Booting` transition, and a boot failure records `Error` instead of wedging the VM. Tests: **167** in `tddy-vm` (0 ignored in a default run) plus **6/6 real-boot acceptance tests** against `debian-12-genericcloud-arm64` (~327 s). (tddy-vm, tddy-service, tddy-daemon, tddy-vm-build)

Design mirrors `~/Code/makers-lt`'s `maker-vm` qcow2-backing-file chaining; no image ever downloaded by this feature — tests reuse an already-built base supplied via `TDDY_CLOUDINIT_BASE_IMAGE`. 65 unit/acceptance tests pass (3 correctly-gated `#[ignore]`d, one run for real against makers-lt's `debian-12-base.qcow2`), `clippy -D warnings` clean. - **2026-07-02** [Feature] **`cloud_init` module — cloud-init image build with image-chaining** — new `packages/tddy-vm/src/cloud_init.rs`: pure argv/document builders (`base_convert_argv`, `overlay_create_argv`, `render_user_data`, `render_meta_data`, `completion_token`, `seed_iso_argv`, `iso_tool_command`, `cloud_init_boot_argv`, `classify_serial_line`) plus the async `build_cloud_init_image` orchestrator (copy base → convert to immutable qcow2 → resolve/generate SSH keypair → render+write NoCloud seed → build cidata ISO via `xorriso`/`mkisofs`/`genisoimage` → create the chained delta overlay → boot QEMU and watch the serial console for a `sha256`-derived completion token, with a durable `<name>-boot.log` transcript and a monitor-socket graceful-shutdown timeout fallback). Reuses `QemuVmArgs::monitor_socket_path`/`send_monitor_command` and mirrors `build.rs`'s progress-reporting and `tokio::select!` line-draining idioms. 22 unit tests pass; the real-boot tests are production tests — `#[ignore]`+`#[serial]` and additionally gated on `TDDY_CLOUDINIT_BASE_IMAGE` (no bundled/auto-discovered image; never run, even with `--ignored`, unless a developer explicitly supplies that env var) — verified to succeed end-to-end multiple times in a nested-virtualization sandbox when supplied (found+fixed a real `set_hostname`-misclassification bug and a `ds=nocloud` boot-speed fix along the way), though still timing-sensitive under that sandbox's fixed budgets.
