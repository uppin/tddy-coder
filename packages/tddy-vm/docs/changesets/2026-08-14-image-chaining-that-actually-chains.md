# 2026-08-14 — **image chaining that actually chains

**Type:** Fix

implicit qcow2 flattening removed from every production path** — `cloud_init.rs` copied its source image into a scratch subdirectory and ran `base_convert_argv` (`qemu-img convert -f qcow2 -O qcow2`) on it, a function whose own doc comment advertised that it *"flattens any prior backing chain on the source into a standalone, immutable base image"*. Every bake therefore produced a full standalone copy plus a delta, so a three-layer "chain" cost three copies of everything beneath it — and because `fs::copy` moves only the overlay file, chaining a layer onto an already-prepared base stranded that base's deliberately **relative** backing reference one directory deeper and died with *Could not open backing file*. Now the imported pristine image is the **only full image in the system**: `base_convert_argv`, `copy_and_convert_base`, `promote_prepared_base_pair` and `move_scratch_output` are deleted, `CloudInitLibraryPaths` loses `prepared_base_output`, and `build_cloud_init_image` chains a delta directly onto whatever image it is given — pristine import or provisioned layer alike — via the new pure `relative_backing_path` (bare basename for a sibling, `../01-base/x.qcow2` across tiers; returns `Result` and refuses a mixed absolute/relative pair rather than emitting a walk that resolves to nothing). Because qcow2 resolves a relative backing path against **the directory holding the referencing image**, not the process CWD, the overlay is created at its final path and never moved, and `run_qemu_img` gained a `cwd` so `create -b <relative>` validates the parent from the right directory. Three defects found by validation, each pinned by a test watched failing first: the overlay is created where the previous bake left a **sealed `0444`** file, and `qemu-img create` opens `O_WRONLY|O_CREAT|O_TRUNC`, so the *second* `tddy-vm-build cloud-init --name X` and every re-issue of `BuildTddyHostImage` died `EACCES` — `unseal_existing_overlay` mirrors `import_base_image`'s unlock-before-overwrite; a **relative** library root made both the output and the backing check resolve under the new cwd, so `tddy-vm-build cloud-init` with no `--library-root` failed 100% of the time (`default_tddy_data_dir()` is the relative `tmp/.tddy` in debug builds) — both paths are canonicalized now; and `create_vm` generated a per-VM keypair that **nothing ever injected into the guest**, so with `BatchMode=yes` + `IdentitiesOnly=yes` every `ssh`/`scp` into a library VM had no way to authenticate — it now writes a per-VM NoCloud seed authorizing that key, attached at both boot sites. `import_base_image` rejects a chained source (reading the qcow2 header's `backing_file_offset` directly) instead of silently stranding it. `qemu.rs` also gains `scp_opts`/`scp_to_guest_argv`/`scp_to_guest`, factored with `ssh_opts` through a shared `client_opts` — separate functions because `scp` spells the port `-P` and reads `-p` as *preserve modification times*, which would leave the port number in the argv as another source path. Guarded by `no_disk_flattening_acceptance.rs`, which scans production sources for a qcow2-source convert and allowlists only the two legitimate raw-to-qcow2 normalisers (`build.rs`, `tddy-build-qemu`). Tests: 208 across `tddy-vm`/`tddy-vm-build`/`tddy-vm-testkit`, 0 failed; `clippy -D warnings` clean. **Not closed and flagged in `docs/dev/TODO.md`:** `VmManager::start` still boots with `seed_iso: None`, so a library VM started through the *daemon* has the same authentication gap; and no layer records its parent's identity, so a re-imported base silently changes the bytes under every child.
