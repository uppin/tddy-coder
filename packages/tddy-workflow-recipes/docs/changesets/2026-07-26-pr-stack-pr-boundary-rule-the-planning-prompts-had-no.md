# 2026-07-26 — pr-stack-pr-boundary-rule: the planning prompts had **no** guidance on PR size or self-containment (the only normative split constraints were dependency ordering, parallelism and branch naming), so "node 1: add the proto RPCs / node 2: implement them" was a legitimate plan

**Type:** Feature

`pr_stack/hooks.rs` `analyze_stack_system_prompt` gains a **"Scoping rules: every PR is self-contained"** block (one node ships the API/schema change + implementation + tests; an explicit list of layer splits that are one node — schema/behavior, endpoint/handler, model/persistence, signature/body; a surface-only node returning `unimplemented` is not a valid PR; an oversized slice splits by **capability** — one source variant, one enum case, one screen, happy path first — each part still end-to-end; sole exceptions a mechanical rename/move or regenerating committed codegen, with a third case routed to a human via the node `description`), and `write_stack_plan_system_prompt` **restates** them under a heading marked *your judgment — the hook cannot check these*, kept distinct from the enforced-validation list: `plan_refinement_goal()` returns `write-stack-plan`, so a rule only in `analyze-stack` would be dropped on the first chat refinement. `pr_stack/mod.rs`'s non-orchestrate `orchestration_system_prompt` fallback carries a one-sentence version; `plan_pr_stack/prompt.rs`'s dead near-duplicate system prompts (`PlanPrStackRecipe` is never instantiated) gain a doc comment marking them superseded and telling a reviver to port the rule across. **Advisory by design** — `validate_stack_plan` sees only the plan fields, never the diff a node produces, so enforcement was considered and rejected (a `description` keyword heuristic is trivially reworded around and rejects legitimate plans); escalation path is a plan-review gate, not a validator regex.
