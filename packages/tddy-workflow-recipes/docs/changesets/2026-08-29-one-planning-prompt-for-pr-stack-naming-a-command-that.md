# 2026-08-29 — one planning prompt for pr-stack, naming a command that exists

**Type:** Bug Fix

the `write-stack-plan` system prompt told the agent to submit "using the `submit` tool with key `stack-plan`", but `advertised_tools` deliberately excludes the CLI subcommands, so no such tool has ever been callable; a live session searched every namespace for `submit`, found nothing, and shelled out six discovery calls later. It now spells out `tddy-tools submit --goal write-stack-plan --data-stdin` with a heredoc as the tdd and bugfix prompts do, warns against building the JSON with `python`/`cat` (only `Bash(tddy-tools *)` is auto-approved), points at `get-schema`, names `$TDDY_SESSION_DIR` as where `stack-plan.yaml`, `pr-stack-plan.md` and `artifacts/exploration.md` land, and drops the `stack-plan-md` submission nothing consumes — `after_write_stack_plan` derives that markdown itself. `write-stack-plan` gains `proto/write_stack_plan.proto`, `generated/tdd/write-stack-plan.schema.json` and a `goals.json` entry, which land together because `build.rs` hard-fails when the registry names a file not on disk. The superseded `plan-pr-stack` recipe carried a second, divergent copy of both planning prompts with the same defects; both recipes now share one source in `plan_pr_stack/prompt.rs` parameterised by recipe name, so they cannot drift again — which also ports the PR boundary contract across, as that module's note asked. Feature [pr-stacking.md](../../../../docs/ft/coder/pr-stacking.md); module [workflow-schemas.md](../workflow-schemas.md).
