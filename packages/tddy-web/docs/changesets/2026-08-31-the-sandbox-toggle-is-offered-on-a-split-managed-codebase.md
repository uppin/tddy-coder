# 2026-08-31 — the Sandbox toggle is offered on a split managed-codebase session, and submit passes it through

**Type:** Feature

`CreateSessionPane` withdrew the Sandbox control on a split placement (`isSplitCodebase`) and blanked `sandbox` to `false` at submit, on the premise that a sandbox resolves a worktree on the daemon running the agent — which a split session has no repository on. That premise predates the workspace tool sandbox: `sandbox = true` now provisions a per-session jail on the host holding the checkout, so on a split placement the flag confines the **codebase host** (B), not the agent (A). The JSX guard hiding the toggle and the `sandbox: isSplitCodebase ? false : sandbox` submit blanking are both removed; the toggle is interactive on a split and its state rides through to `StartSession`. Recipe withdrawal and `dangerouslySkipPermissions` withdrawal on split are unchanged — a recipe's tooling and the deny-list-safety guarantee still resolve against the agent host. Cypress `CreateSessionCodebaseHostAcceptance` inverts the two cases that expected the sandbox withdrawn and adds cases pinning `sandbox: true` (checked) and `sandbox: false` (unchecked) on a split placement. Depends on `split-sandbox-orchestration`, which removed the daemon's `invalid_argument` refusal of split + sandbox. No proto, no Rust, no new RPC. Tests: 21 Cypress cases in the spec, `bun run build` clean. Feature [remote-managed-worktree.md § Sandbox: placement-dependent semantics](../../../../docs/ft/daemon/remote-managed-worktree.md).
