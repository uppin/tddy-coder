# code_index.CodeIndexService

How this crate is put together, and why each part is where it is.

## Two lifetimes over one implementation

`main.rs` builds **one** `CodeIndexServiceImpl` and never a second. Single-shot calls the generated
trait method on it directly; each transport wraps the same `Arc`:

| Transport | Wrapper |
|---|---|
| gRPC (TCP and UDS) | `CodeIndexServiceTonicAdapter`, generated by `tddy-codegen` |
| stdio | `CodeIndexServiceServer::from_arc`, whose doc states it exists so one implementation can be served over more than one transport |

`build_code_index_entry` is the entry point for a host registering a *single* service; it constructs
its own `Arc` internally, so a process serving several transports takes the `Arc` one level up
instead. Two implementations over one `LspRegistry` would share the language servers but **not**
`WorkspaceIndex`'s per-root queue, and two clients on one root could then collide on
each plan's journal, and the one root's plan store would be split in two.

Single-shot passes prost structs in and out with no encode or decode, which is what makes it the same
code path rather than a second one.

## Codegen

`build.rs` runs three passes over `proto/code_index.proto`, the shape `tddy-terminal-rpc`
established:

1. `prost_build` with `TddyServiceGenerator { generate_rpc_server: true, generate_tonic_adapter:
   true }` — the async trait, the `tddy-rpc` server that stdio registers, and the tonic adapter;
2. `tonic_build` into `OUT_DIR/tonic_code_index` with `.extern_path(".code_index",
   "crate::proto::code_index")`, so both trait impls speak identical Rust types and nothing is
   re-encoded when a request crosses from one transport to the other;
3. a descriptor-set-only pass, so a host can merge this service into gRPC reflection without
   re-parsing the schema.

The proto declares a bare `package code_index;`, matching every other crate-owned proto in the
workspace. A versioned name for one new service would be the partial adoption the backlog forbids.

## Warm state, per workspace root

A request names a path; `WorkspaceIndex::workspace_root_of` turns it into the root its state is kept
under with `tddy_lsp::registry::workspace_root_for`, which follows `cargo locate-project --workspace`,
bounded by the repository. Walking outward from the path, the root is the nearest `Cargo.toml` that
declares `[workspace]` (or a `[workspace.*]` table); failing that, the nearest manifest, since a
package in no workspace is its own root; failing that, the path itself. The walk stops at the first
directory holding `.git` — a directory for a checkout, a file for a linked worktree — so a worktree
nested inside another checkout (`<main>/.worktrees/<name>`) is served its own tree, never the
enclosing one. An unreadable manifest on the walk is a `FailedPrecondition`, not skipped.
`tddy-lsp-executor` resolves its roots with the same function.

| State | Held by |
|---|---|
| rust-analyzer process and its `LspClient` | `tddy_lsp::LspRegistry`, keyed `(root, Rust)`, idle-reaped, respawned when its task dies |
| `BackendRegistry` / `RustBackend` | rebuilt per request through `runner::registry_for` — so the readiness probe is re-paid even against a warm server, and holds the same quiescence and health rules as the cold path |
| rust-analyzer's latest `experimental/serverStatus` | `LspClient::server_status`, kept on the client for every reader. A status is sent only on a transition, so without it a request arriving after another had drained the transition would never learn the index is degraded |
| Open-document versions | `LspClient`, per URI |
| The source-tree snapshot taken at the previous request | `WorkspaceIndex`, per root, replaced together with the crate-graph latch |
| Complexity scores | process-wide, keyed by a hash of the content scored |
| Plan store (`PlanStore`) | `WorkspaceIndex`, per root, across requests; `plan_flush.rs`'s background tick flushes plans dirty for over a second, and `serve.rs` / `main.rs` flush every plan at shutdown and exit |
| The root's progress (`RootProgress`) | the root's `GraphLoad`, attached when `record_use` first hands out its server, for that server's life |
| Why a root's server could not start, or died unasked | `RootSignals`, per root, until the root is served again |
| Stale operations of the loaded plans | the plan store, in memory, for the life of a load; never serialised into a plan |
| `Overlay`, `PositionLedger`, `Journal` | per request, never shared |

**A warm server is told what changed on disk between requests.** The client auto-acknowledges
`client/registerCapability`, so rust-analyzer registers its own file watching, but on this workspace
it does not see a module an earlier `apply` wrote or a file written by hand. So `client_for` reads
the root's `*.rs`, `Cargo.toml` and `Cargo.lock` files before handing a server over — skipping
`target/`, `node_modules/` and hidden directories, and following no symlinks — and compares them by
modification time and length with the snapshot kept for the previous request. A server this process
already held is sent `workspace/didChangeWatchedFiles` naming each file created, changed or deleted,
and rust-analyzer re-reads each one; a newly spawned server is sent nothing, since it loads the tree
itself. It is a notification rather than an open and close, so a document some request holds open is
unaffected. A tree that cannot be read is a `FailedPrecondition`. The walk costs about 0.2 s per
request on this repository (1,843 files). No filesystem-watching dependency is taken.

**Loaded plans are kept current from the same comparison.** The files `client_for` finds changed since
the previous request are also what a person or a pull changed, and a loaded plan's item anchors in them
may have moved or stopped meaning what they meant. `plan_upkeep` hands the `.rs` files to the store to
re-resolve, through the warm client; the files the daemon's own applies wrote are discounted, because
the apply already folded each operation into every loaded plan. Resolver refusals become stale reasons
(`item changed`, `item not found in <file>`). A server reaped while idle reports nothing changed, so
edits made in that window are caught at apply by the resolver's fingerprint refusal rather than by
`ListPlans`.

## Root progress

**One fold per root, for the server's whole life.** When `record_use` first hands out a root's server it
attaches a `GraphLoad`, which subscribes to the server's notifications and folds every
`$/progress` and `experimental/serverStatus` through an **unthrottled** `ServerChatter` into a
`watch<RootProgress>`:

| Field | Meaning |
|---|---|
| `quiescent` | the server's **latest** `serverStatus` said `quiescent: true`. Not a latch — an edit that sends rust-analyzer back to work makes it false again. False before any status |
| `loaded` | the first quiescence, never unset — the crate-graph latch `Warm` answers `ready` on |
| `phases` | every work-done token in flight, in begin order (`ServerChatter::active_phases`): title from its `begin`, latest message, highest percentage |
| `current` | the phase reported on most recently and the highest percentage it reached (`ServerChatter::current`) |
| `furthest` | the last line carrying the furthest percentage any phase reached (`ServerChatter::furthest`) |
| `line` | the latest line worth showing |

Because the fold starts at spawn, a watcher that arrives mid-load reads the phases already running by
name rather than reports whose `begin` it never saw. A notification gap (`NotificationEvent::Lost`) calls
`ServerChatter::lost_sight`, so a phase whose `end` was lost is dropped at the next quiescence unless it
reported again; its title is kept, so a phase still running reappears named. The subscription is
taken within `fake_lsp`'s first-notification delay of the handshake, so no `begin` is missed in tests.

**What "loading" means.** Every reading of a root's state — `WatchRoot`, `Warm` and each navigation
answer — maps `quiescent` through `state_of_quiescence`: `READY` when the latest status was quiescent,
`LOADING` otherwise, including before any status. A root no live server holds is `IDLE`; one whose server
could not start, or exited without being let go, is `FAILED` with `error` saying why until the next
attempt. rust-analyzer always sends the extension because the daemon advertises
`serverStatusNotification`. A server whose launch does not ask for it — an extension language's — is read
by `Readiness::AfterInitialize`: `READY` (and loaded) from the moment its handshake completed, whatever its
notifications say. A root holding both kinds keeps one fold, Rust's
([backlog](../../../docs/dev/todo/2026-10-22-mixed-root-index-progress-follows-rust-only.md)).

**`IndexProgress` on the wire** (`reported`): `phase` / `percentage` are `current`'s — the phase the
server reported on most recently, at 0% until it reports a number, never moving backwards on a sub-step
carrying no number; `furthest` is the cross-phase figure (rust-analyzer finishes *Roots Scanned* at 100%
within seconds and then spends minutes building and indexing, which a single cross-phase maximum would
hide); `line` what it is doing; `state` (`IndexState`); `phases` (`ActivePhase { title, message,
percentage }`, percentage absent when the phase never reported one); `error` when `FAILED`. `ready` is
`Warm`'s "this stream is done" flag and is false everywhere else.

**`WatchRoot(workspace_root)` never starts a server.** It opens with the root's current state and sends
every change after, until the caller leaves:

- a root no server holds sends `IDLE` (or `FAILED` with its reason), then waits on `RootSignals` —
  fired when anything (a warm, a navigation request, an agent's code tool) attaches a server or a start
  fails — never on a timer;
- a held root forwards every change of its `RootProgress`, deduplicated; the progress sender dropping is
  the server going away, after which the root reports `IDLE` (or `FAILED`) again.

**`Warm` is "start the server, then follow the root until loaded".** It calls `client_for(root)` and
forwards the root's progress through the same `next_change` wait until `loaded`, which it sends with
`ready: true`; a server that goes away mid-load ends it `UNAVAILABLE`, and a start that fails is refused
with the reason (and recorded for `WatchRoot`). Idempotent: a loaded root answers `ready` at once. Three
things end it — the graph loading, the server going away, the caller hanging up.

The printed progress of the single-shot console is throttled to one line per token every two seconds;
the streams are structured events, so their chatter is unthrottled — a client that wanted the 50% it
was never sent cannot ask again.

## Navigation

`Definition`, `References` and `Hover` take `{workspace_root, file, position}` and answer from the
warm server of the file's language (`route_of`, then `client_for_route` — `client_for(root)` for a `.rs`
file), through `LspClient::{definition, references, hover}`.

**Index state.** Each answer carries `state` (`LOADING` or `READY`), read from the server's latest
`serverStatus` through `ServerChatter` (`index_state_of`). `tddy-lsp`'s reader records a status before it
routes the response that follows it, so the state is the one the answer was given in. rust-analyzer
answers empty while its crate graph loads, so an empty answer with `LOADING` means "not known yet", and
only an empty answer with `READY` means the code does not resolve. Navigation never waits for the graph:
a cold load takes minutes, and holding a query is the caller's choice (the daemon's `CodeSession` holds
on a stream the pane can cancel).

**Coordinates.** A `SourcePosition` is a one-based line and a one-based **byte** column, the
coordinates every other RPC in the service uses. The language server speaks zero-based positions, and
the conversion belongs to this module, so no caller sees an LSP position. The LSP client negotiates
`positionEncoding: utf-8` and refuses a server that does not answer in it, so a column converts by its
offset alone (`character + 1` on the way out) and the daemon performs no UTF-16 arithmetic.

**Locations.** A `CodeLocation` carries `file`, a `range` and `outside_root`. A location inside
`workspace_root` is returned relative to it; one outside it (a dependency, the standard library) is
returned as an absolute path with `outside_root` true, which a caller that can only open files of the
root must not offer to open. File URIs are percent-escaped on the way to the server and decoded on the
way back.

**What is refused**, all before the server is asked:

| Request | Status |
|---|---|
| Empty `file`, an absolute `file`, or one containing `..` | `InvalidArgument` |
| A file that is not `.rs` and that no installed language claims, or whose language has no configured server | `InvalidArgument` |
| No position, or a line or column of 0 | `InvalidArgument` |
| A file that cannot be read | `NotFound` |
| A language-server failure | the class `status.rs` assigns it |

**Freshness.** The file's current contents are sent to the server (`sync_document`) before each query,
so the answer is about the text the caller read, not an older copy the server held.

### Extension languages

A host built with supports (`build_code_index_entry_with_supports`, `CodeIndexServiceImpl::with_supports`;
`main.rs` registers the built-ins, then every installed Zed extension's languages) routes a file by
`route_of`: a `.rs` file is Rust's, whatever an extension also claims; any other file goes to the support
that claims it when that support has a launch (`Route::Extension { language, launch }`), and is refused
otherwise. `client_for_route` spawns or reuses that language's server under `LspKey { root, language }`
from the same allow-list (`SupportRegistry::allow_list`), records the language against the root so
`warmth_of` sees it, and opens documents as the launch's `language_id`. It is told of no tree changes —
only Rust sources are tracked
([backlog](../../../docs/dev/todo/2026-10-22-extension-servers-are-not-told-of-tree-changes.md)); the
document asked about is announced with its current text on every request.

`serves_workspace(root, supports)` is the question every "does this root get an index" caller asks: a
Rust workspace is served; with `supports` handed over, so is a tree holding a file an installed language
with a launch claims. With `None` (no extension language registered) a non-Rust tree is not.

`Apply` reaches the same servers: `installed_clients_for` spawns one per installed language a file of the
plan belongs to (`runner::installed_launches_for`), the run's `Options` carry them, and the registry the
loop resolves through builds each installed support's backend over its own server — so an extension
language's `rename_symbol` goes to `textDocument/rename` on that server. A server that will not start
refuses the run before anything is written.

## Symbols and diagnostics

`Symbols` and `Diagnostics` answer what an agent's `LspSymbols` and `LspDiagnostics` tools ask, from the
same warm server and in the same coordinates as navigation.

- **`Symbols{workspace_root, file, query}`** — without a `query`, the symbols of `file` through
  `LspClient::symbols`; with one, the root's symbols whose names match it through
  `LspClient::workspace_symbols`, and `file` is ignored. Each `CodeSymbol` carries `name`, `kind` (the LSP
  `SymbolKind` code, passed through), a `CodeLocation` and the `container`, when there is one.
- **`Diagnostics{workspace_root, file}`** — what the server reports wrong with `file` through
  `LspClient::diagnostics`. Each `CodeDiagnostic` carries a one-based byte `SourceRange`, the LSP
  `severity` code, the `message` and the `source` (for example `rustc`), when the server names one.

A request naming a file is refused by the checks navigation applies, with the same statuses (the
table above), and the file's current contents are sent to the server before the query. A `Symbols`
request with a `query` names no file, so it is neither checked nor synced: it goes to the root's server
as it is.

## Cancellation

`tddy_rpc::RpcService` passes a handler no token, no deadline and no context, and `ServerEngine`'s
peer-disconnect abort is not in the tonic path at all. Aborting a future also stops nothing that is
blocking, and the restructure engine is synchronous under `spawn_blocking`.

So each long operation owns a `CancellationToken` checked *inside* the engine's poll loops, and **a
send failing into the response stream's dropped receiver is the signal that cancels it**. That is the
only disconnect signal a handler gets, and it is why the long operations stream.

## The health gate and the compile gate

Both are the restructuring library's, reached through the same entry points the CLI uses, so the
daemon path cannot drift from the cold one. See
[`tddy-code-restructuring/docs/readiness-and-gates.md`](../../tddy-code-restructuring/docs/readiness-and-gates.md).

- **A degraded index is refused at the first operation** (`ServerDefect`, quoting rust-analyzer's
  message) — `health` anything but `ok`, `warning` included, because that is how a failed build
  script is reported. `Warm` still reports `ready` for such a root: it answers "is the graph loaded",
  and the gate refuses when an operation first asks it something.
- **`Apply` is bracketed by `cargo check --all-targets`** over the packages it touches. The baseline
  runs after the cheap read-only refusals and before `.restructure/` is created; the result check runs
  before the outcome event is emitted, so a stream never ends with "applied N of N" over a tree that
  does not compile. Both checks are killed when the request's cancellation token fires.

### Transactional groups

A plan's [transactional groups](../../../docs/ft/coder/rust-code-restructuring.md#transactional-groups)
are judged inside the apply loop by the library's `runner::group_gate::GroupRun`, the same type the
command line's loop uses. At a group's first member the loop journals `group_started` and each member's
pre-images; at its last it runs `cargo check --all-targets` over the packages the group touched, under
the request's cancellation token, then either journals `group_completed` and refreshes the members into
the plan store together, or restores the pre-images and journals `group_rolled_back`. Any failure while
a group is open rolls it back and returns the original error; only `GroupDoesNotCompile` names the gate.
Cancellation is checked before each operation: a request whose caller has gone rolls the open group back
at once rather than leaving it for a resume, and a cancel during the group's own check leaves it open
(`CallerStopped`) for the next resume to roll back. A resume (`--resume`) rolls an open group back before
it runs anything. `stop_after` is judged only where a group would begin.

## The language server

`main.rs` builds the process's `LspAllowList` from its supports: Rust from `--rust-analyzer <PATH>`, or
the bare `rust-analyzer` resolved on the process's own `PATH` when the flag is absent, then the launch of
every installed extension language whose server is configured. The handshake (`client_capabilities`, `server_settings`) is fixed at spawn, which is
why this process owns its registry rather than sharing `tddy-daemon`'s. The toolchain rust-analyzer
loads a workspace with (`cargo`, `rustc`, `RUST_SRC_PATH`) is whatever this process's environment
says; `tddy-daemon` sets it from `index_daemon.env`.

**Installed extension languages.** `main.rs`'s `installed_languages()` loads every installed Zed
extension's languages (`tddy_zed_extensions::InstalledExtensions::with_installed_extensions` over
`ExtensionsDir::resolve()`), logs each grammar that does not load once, and hands the registry to
`CodeIndexServiceImpl::with_supports`; an unreadable extension manifest stops the process at start.
`WorkspaceIndex::with_supports` holds it and puts it in every run's `Options::installed`
(`serve_check`, `anchor_covering`); `build_code_index_entry_with_supports(ports, supports)` is the
same for a host that registers the service itself. An `Anchors` request on a file only a server-less
installed language claims asks `client_for` nothing — no rust-analyzer is started for it — and nor does
a `Snapshot` whose item anchors all lie in such files (`Options::plan_item_anchors_need_a_server`). The
allow-list is the registry's (`SupportRegistry::allow_list`): Rust's launch, then every installed
language whose server is configured.

A program that cannot be started reaches the caller as `LspError::ServerNotFound` (`NotFound`) or
`LspError::Io` (any other spawn failure) — `FailedPrecondition` and `Internal` in [Refusals](#refusals) —
not as `ServerExited`.

## The spawn record

`--spawn-record <PATH>` names an append-only JSONL file the daemon writes, one object per line, of
every process it starts: a `start` line when a process exists (argv, cwd, pid, the **names** of its
environment) and an `end` line when it is waited on (exit code, terminating signal, or a failed
spawn). It is the daemon's half of
[what a run executes](../../../docs/ft/coder/rust-code-restructuring.md#what-a-run-executes).

The observer is built once in `main.rs` from `--spawn-record`, handed to the `LspRegistry` with
`.with_spawn_observer(...)`, and rides inside the registry: `WorkspaceIndex::spawn_recorder()` hands
the same observer to the `Options` a `check` or `apply` builds, so a language server's start and an
operation's `git`/`cargo`/`rustfmt` land in the one file. The registry's records carry
`origin: "lsp"`; an operation's carry `origin: "engine"`.

The record never truncates, so a restarted daemon appends after its predecessor's lines. Arguments
are redacted and the environment is recorded as names only. A write that fails is logged and
dropped: it never fails a request.

**The daemon's own exit is not written here.** The daemon `exec`s nothing and writes no line about
itself; `run-index-daemon` launches it as a background child of a watcher shell whose `wait` writes
the `index-daemon` `end` line — the one thing a `SIGKILL` cannot do from inside. See the script's
own narration for the file's location.

## Refusals

`status.rs` holds one `match` per error type — `RestructureError`, `AnalysisError`, `LspError` — each
naming every variant with no catch-all arm, so a variant added later is a compile error here rather
than a silent `Internal`. An unclassified error maps to `Internal` deliberately: a refusal a caller
cannot act on is exactly what that class means, and the fix for a mis-classified one is a new
variant, not a cleverer default.

The compile gate's two variants map by who can fix them: `BaselineDoesNotCompile` is
`FailedPrecondition` (nothing was written, and the same request fails until the tree is repaired),
`AppliedTreeDoesNotCompile` is `Internal` (the executor's own accepted operations produced it).
`GroupDoesNotCompile` is `FailedPrecondition`: the group was rolled back, the tree is as the operations before it left it, and the same request fails identically until the plan or the code changes.
`UntrackedMoveSource` is `FailedPrecondition`: nothing of the operation was written, and the same request succeeds once the file is `git add`ed. `ServerStalled` is `DeadlineExceeded`, like the other "the index did not get there" refusals: rust-analyzer said it was loading and then said nothing new for the loading-silence bound.

## Testing

Every suite runs against `fake_lsp`, `tddy-lsp`'s deterministic fake, reached through a re-declared
`[[bin]]`. A real rust-analyzer costs minutes and is a production test by this repo's definition.

| Suite | Covers |
|---|---|
| `code_index_service_acceptance.rs` | Every RPC dispatched at the registered coordinate through `handle_rpc` (navigation answers, root-relative and one-based, come from `fake_lsp` started with `--answers-in-its-workspace`, which reports its canned locations under the client's `rootUri`), plus the coordinate-integrity trio — including one test that reads the `.proto` off disk and asserts the published constant matches the schema — and an `Apply` the compile gate fails |
| `root_progress_acceptance.rs` | `WatchRoot` and `Warm` over the per-root fold: a root no server holds reports `IDLE` and starts none; a watch reports the load a navigation request started; a server that cannot start reports `FAILED` with the reason; a watch joining mid-load names every phase already running; a warm reports `ready` only once loaded and carries the active phases; a definition asked while loading says `LOADING`, once loaded `READY`. Driven by `fake_lsp --loads-crate-graph-on-signal`, which begins two overlapping phases and holds until a file the test names appears, so "mid-load" is deterministic without sleeps |
| `dual_transport_acceptance.rs` | The binary as a process: single-shot exit codes, both transports concurrently, stdout silence under `--stdio`, fail-fast with no transport |
| `tree_changes_acceptance.rs` | A warm server told of a module written since its last request (created and changed), of one removed (deleted), of each change once, and of nothing when the tree has not changed — against `fake_lsp`, which replays the notifications it received as `tddy/watchedFileChanges` |
| `extension_references.rs` | A host over `demo-toml` with `fake-ls` configured: `References` on a TOML file is answered by the extension's server; an extension-only worktree is served (`serves_workspace`); an `Apply` of an item-anchored `rename_symbol` renames the key through `fake_lsp --answers-rename` |
| `extension_readiness.rs` | A server without `serverStatus` reads `READY` after `initialize`; Rust's rule still reads a silent server `LOADING` |
| `live_plans_acceptance.rs` | The apply loop folding a test-binary move into another loaded plan's file hint and flushing it, and an unloaded plan staying byte-identical after another plan applies |
| `activity_log_acceptance.rs` | The whole journal of one request, through a capturing logger — which caught a double-logged outcome that no test of the pure composer could see |
| `warm_index_production.rs` | `#[ignore]`. Real rust-analyzer; the index-reuse claim, asserted as a ratio against the cold run the test creates itself |
| `detached_daemon_production.rs` | `#[ignore]`. The real `run-index-daemon` script: the daemon outlives its starting shell, runs with the dev shell's whole environment, and a restart announces the daemon it started rather than the previous one's log line. A drop guard owns the runtime directory and runs `--stop` when a test ends, pass or panic. The restart test guards a scheduling race it cannot force, so a pass is evidence, not proof |

Run the production tier deliberately:

```bash
./dev cargo test -p tddy-index-daemon --test warm_index_production -- --ignored --test-threads=1
./dev cargo test -p tddy-index-daemon --test detached_daemon_production -- --ignored --test-threads=1
```
