# 2026-08-29 — `subagent_status` waits, instead of being polled

**Type:** Feature

`subagent_status { agent, waitFor: "ready", timeoutMs }` parks until the named agent stops being `connecting`, then returns the report a plain read returns plus `timedOut`. Polling an MCP tool costs a whole model turn per look, and an attach returns before the agent is usable, so the main agent's first move was often a prompt refused for a clone still provisioning. `agent` is the wait's **target, not a filter** — a plain read still carries every row when one is named, and a call that asked for no wait carries no `timedOut` at all. The wait parks on a new snapshot generation (`LiveAgentRoster::subscribe_to_snapshots`, a `watch` so subscribing before reading cannot lose the frame that lands between the two) rather than on `rev`: a status republishes at the revision already in force, so a `rev`-driven wake would sleep through the one transition it exists to catch. Settling is narrower than promptability — only `connecting` keeps it parked, because a failed checkout is not something waiting fixes and parking to the deadline would report that failure later and call it a timeout; `unknown` settles it too. An id no row ever bore is refused naming the ids there are (settling it silently would answer a misspelled agent with `timedOut: false`, which reads as "it is ready"), while an id seen and then gone is a detach and simply stops being listed. `timeoutMs` defaults to 30 s and is capped at 120 s. `apply_snapshot` is split around `replace_entries_with` so the generation publishes after the lock guard drops and a frame too old to apply wakes nothing — no behaviour of its three existing arms changes.
