# 2026-08-14 — **`SessionToolTransport::LiveKit`

**Type:** Feature

reaching a worktree on another daemon** — a third binding for the dispatch `tddy-tools` already speaks, beside the sandbox's stdio socket and the relay's HTTP endpoint; `tddy_livekit::RpcClient` already implements `RpcClientTransport`, so what is new is the request envelope (`SessionToolEnvelope`: the sandbox path sends an empty `session_id` because its socket implies identity, a remote daemon resolves the worktree from that id against its *own* sessions base). Detection is `SandboxIpc → LiveKit → DaemonHttp`, and a *partially* configured LiveKit env is reported as `IncompleteLiveKit` naming the missing variables rather than degrading to an HTTP relay whose URL is empty — that silent fall-through returned `relative URL without a base`, naming the relay for a LiveKit fault. Results arrive over `StreamExecuteTool` and a stream ending without its `last` frame is an **error** with the prefix discarded: returning it hands the agent a truncated file that reads as whole. One room is held per destination (`LiveKitRoomCache`, per-key `OnceCell` so parallel MCP calls connect once; failed connects are not cached) with clients from `LiveKitRpcClientFactory::for_room` — building them directly leaked a `subscribe()` loop per call, harmless only while every call had its own short-lived room. `clamp_remote_blocking_args` *inserts* the block ceiling when a tool names none, because the engine's own 30 s default is exactly the deadline the ceiling exists to stay under. Every dispatch failure now logs at `error`. Feature [remote-managed-worktree.md](../../../../docs/ft/daemon/remote-managed-worktree.md).
