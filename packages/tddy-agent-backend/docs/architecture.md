# tddy-agent-backend architecture

## Overview

The coding-agent backends — the one spec-configured headless backend that runs Claude Code, Cursor,
Codex, Oz and any headless agent a YAML file declares; Claude, Codex and OpenCode over ACP; and the
mock and stub backends — with the stream adapters that read their CLI output, token accounting, the
per-turn process groups and session pointer a headless turn runs with, and the hook and argv
builders they launch with.

### Dependency rule

Workspace dependencies: `tddy-workflow`, `tddy-session-store`, `tddy-toolcall`. It does **not**
depend on the workflow engine: the only things a backend takes from a recipe are `GoalHints` and
`PermissionHint`, which are plain data in `tddy-workflow`. `WorkflowRecipe` names `CodingBackend`,
not the other way round, so the edge runs one way, engine → backend.
`packages/tddy-core/tests/core_facade_shape.rs` pins it
(`the_agent_backend_does_not_depend_on_the_workflow_engine`). `agent-client-protocol` and
`tokio-util` are dependencies here, for the ACP backends.

`tddy-core` re-exports this crate whole (`pub use tddy_agent_backend::*;`), so every `tddy_core::{backend, stream, token_accounting, claude_hooks, cursor_hooks, spawn_env, provider_route}::…` path consumers name resolves unchanged. New code should name `tddy_agent_backend` directly.
`backend::write_codex_thread_id_file` is `pub` because the workflow engine calls it across the
crate boundary. It is not API.

## Backend (`backend`)

- **CodingBackend**: Async trait for invoking LLM-based coders. Implementations: `SpecHeadlessBackend` (every headless CLI agent), `ClaudeAcpBackend`, `CodexAcpBackend`, `OpenCodeAcpBackend` (production), `MockBackend`, `StubBackend` (testing/demo). `SpecBackend` (headless or ACP, built from an agent spec) for CLI dispatch; its headless arm holds a `SpecHeadlessBackend` built from that agent's spec. `SharedBackend` wraps `Arc<dyn CodingBackend>`; backend created once per run. **`action_invoke_cache_eligible`**: production backends default **true** so **`BackendInvokeTask`** may reuse a prior successful **`tddy-tools submit`** result; **`MockBackend`** returns **false** so harness-driven invokes stay aligned with explicit submits; **`StubBackend`** supports invocation counting for tests.
- **SpecHeadlessBackend** (`backend/spec_headless.rs`; a spawned turn is read to its end by `spec_headless/turn_read.rs`): the one headless workflow `CodingBackend`, one per agent spec, built by `tddy_coder::headless_from_spec::headless_backend_from_spec(agent, tools_dir, host)`. `new(renderer: Arc<dyn HeadlessRenderer>, protocol: HeadlessProtocol, agent: RoutedAgent)`, `with_turn_deadline(Duration)`, `with_model_listing(HeadlessModelListing)`, `with_progress(f)`, `with_provider_route(HarnessRoute) -> Result<Self, RouteRefusal>` (refused through `agent_routable`, naming the product, for a spec with no `route` section), `protocol()`. No branch names an agent; a turn maps the `InvokeRequest` onto a `HeadlessTurn` as the spec's protocol says (fields under [Adapters](#adapters-adapters)): the goal's hints bind `goal_params` (a param named `permission_mode` fills `{permission_mode}`); the system prompt goes as a file through the `append_system_prompt` slot (`flag` — inline text is written to a temporary file the turn removes) or in front of the prompt after a blank line (`prepend`); the agent's tool server is registered when `workflow_mcp` is set (a spec with no `tddy-tools` dep is then an error) and the approval tool `mcp__tddy-tools__approval_prompt` with it when `approval_tool` is; a provider route's args ride as `route_args` and drop the request's model as `route_model` says; a `Fresh` session id is passed (`fresh_session: caller`) or left to the agent to mint (`agent`); registration files go to the session directory or the working directory (`scratch`; `session_dir` with none in the request is refused). The goal's allowed tools reach no agent whose spec declares `tool_allow: unsupported`.
  - **Environment.** The child starts from exactly the env `SpecHeadlessBackend::child_env` renders, with nothing inherited (`agent_env`, below): the invocation's whole env first — the base set's variables of this process, the spec's `pass_env`, then the spec's `headless.env` rendered by `render_env` (`{session_dir}`, `{self_exe}`; a value naming `{session_dir}` when the request has no session directory is refused, never set with the placeholder) — then the provider route's env and secret env, each replacing a variable of the same name, the precedence an ACP launch has, where the route env is appended after the computed env. `PATH` is then replaced by the running executable's directory ahead of the process's `PATH`. The one `TDDY_*` variable an agent sees is Codex's `TDDY_CODEX_OAUTH_OUT`, which `codex.yaml` declares for its OAuth capture ([backlog](../../../docs/dev/todo/2026-11-05-codex-oauth-out-env-in-headless-agent.md)). Its tools find the session through the session pointer (below).
  - **Working directory.** A turn runs in the request's `working_dir`; a request with none is refused, never run in the process's directory. The rendered files (an MCP registration, the temporary system prompt) and the session pointer are written through `TurnFiles` — those under the working directory git-excluded, so it must be a git checkout — and removed when the turn ends, however it ends.
  - **Process and deadline.** The program runs in a process group of its own (turn processes, below); stdout is read through the spec's stream adapter on a blocking thread and the exit judged by the adapter's `exit_ok`. A turn has a deadline — `DEFAULT_TURN_DEADLINE` (4 h) unless `with_turn_deadline` sets one: an overrun kills the group and fails `"<agent> turn did not end within its <deadline> deadline; its process group was killed"`. Dropping a turn's future kills its group and no other. A finished turn waits at most `STDERR_GRACE` (2 s) for its stderr to close.
  - **Result.** A failed turn is `"<agent> exited with code <n>: <failure_detail>"` (no `: …` when the adapter's detail is empty) — `BackendError::InvocationFailed` displays its message as it is. A response carries the child's stderr whenever it left any, one rule for every agent. Progress events go to the request's `progress_sink`, else the `with_progress` callback; with `agent_output` set, no sink and `TDDY_QUIET` unset, raw agent output goes to stderr for the plain CLI.
  - **`name()`** is the spec id (`claude`, `cursor`, `codex`, `oz`, or a YAML-only agent's), which the workflow engine's Codex thread-id swap and the context-glob and model tables key on. **`list_models`** runs the spec's model listing (`models.list_command` rendered with the spec-resolved binary, read by its models adapter) under `MODEL_LISTING_DEADLINE` (30 s), from exactly `HeadlessModelListing.env` (the agent env the daemon computed; nothing inherited); a binary that fails, overruns or lists nothing is an error. A spec with no listing answers from its `curated_models()`.
  - Tests: `tests/spec_headless_turn_deadline.rs` (a turn past its deadline has its whole group, grandchild included, killed; two concurrent turns cancel only their own), `tests/headless_protocol_unit.rs` (goal params, route-replaces-model, `render_env`, each adapter's `failure_detail` and transcript, turn files and the pointer), and `tddy-coder/tests/spec_headless_backend.rs` (the four built-ins and a YAML-only agent through their real specs against stub CLIs: argv, MCP files, session ids, error texts, the absent `TDDY_*` variables, the pointer).
- **SpecBackend** (`backend/spec_backend.rs`, `#agent-tools 16/19`): the workflow backend `tddy-coder --agent <id>` runs for any registry agent, built by `tddy_coder::spec_backend_build::build_spec_backend`. `SpecBackend { Headless(SpecHeadlessBackend), Acp(SpecAcpBackend) }` delegates `invoke`, `name` (the spec id), `submit_channel`, `action_invoke_cache_eligible` and `list_models`; `transport()`, `with_provider_route(route) -> Result<Self, RouteRefusal>`. Nothing in it names an agent. **Transport rule** — `SpecTransport::chosen(agent, declares_headless, declares_acp, asked)`: a transport asked for that the spec declares is taken; nothing asked and both declared → `Headless`; one declared → that one; asked for one not declared → `SpecBackendRefusal::TransportNotDeclared`; neither declared (a PTY-only agent such as `muse`, `warp`) → `SpecBackendRefusal::NoTurnTransport`. Each refusal names the agent; none falls back to another agent.
  - **SpecAcpBackend**: an ACP agent's workflow backend from its spec's `coding_agent.acp` section — `new(RoutedAgent, AcpAgentCommand)`, `with_hooks(adapter, deps)` (the hooks adapter the spec names and the deps it reads), `with_session_open_deadline(Duration)` (default `SESSION_OPEN_DEADLINE`), `with_provider_route`. The driver starts on the first turn: route env, then the adapter's `prepare`; the adapter's open scope brackets each session open, one open at a time, and a hooks failure (a failed `codex login`) is the error reported in place of the session error it followed. The request's system prompt is merged into the prompt (`merge_codex_prompt`), never dropped. A session open past the deadline is refused as ``the ACP agent `<id>` did not open a session within <deadline>; it is refused rather than waited on``.
  - **`SharedBackend::stub()`**: the shared `StubBackend` (`name()` `stub`), the test double that replaced `SharedBackend::from_any(AnyBackend::Stub(…))`.
  - Tests: `tests/spec_backend_unit.rs` (the transport rule, `name`, `transport`, `stub()`), `tests/spec_backend_integration.rs` (a dropped-in ACP agent that never answers `session/new` refused at its deadline naming it; a spec without a `route` section refusing a route).
- **Turn processes** (`backend/turn_process.rs`): the spawn and cancel core both headless drivers share. A turn's child leads a new process group, its environment cleared and replaced by the computed env (`apply_agent_child_env`), stdout and stderr piped; its `TurnGroup` kills the group on drop unless the leader was reaped. The groups of the turns running now are registered: `kill_running_turns()` (re-exported; `tddy-tui`'s Ctrl+C calls it) SIGKILLs every one and returns whether any ran, and `RunningGroup::new(pgid)` registers a group spawned elsewhere (a conversation's CLI) until it drops. There is no process-wide child slot, so concurrent turns never reach each other's processes. A finished turn does not kill members of its group still running (an MCP server, a backgrounded command); `STDERR_GRACE` bounds the wait on them.
- **Session pointer and turn files** (`session_pointer.rs`, `turn_files.rs`): before each workflow turn whose request names a toolcall socket, the backend writes `<workdir>/.tddy/session.json` (`SESSION_POINTER_FILE`) — a `SessionPointer { socket: Option<PathBuf>, repo_dir, session_dir, remote, notify, owner }` (`repo_dir` is the turn's working directory, `remote` is `RemoteToolEnv::env_pairs()` by variable name, `notify` the operator-notify session `tddy-tools notify` reads, by variable name, `owner` the `SessionPointerOwner { pid, host }` serving the session — `SessionPointerOwner::this_process()` for a turn's pointer; empty and absent fields are omitted, unknown fields refused, so a `tddy-tools` older than a field rejects a pointer carrying it). `this_host()` is `gethostname` as `hostname` prints it, and asserts when the call fails: its 256-byte buffer is above every `HOST_NAME_MAX`. `SessionPointerOwner::is_on_this_host()` compares the owner's host with it, and `is_running()` probes the pid with signal 0 (`EPERM` counts as running) — meaningful only on the owner's host. A pointer without `owner` is read as an unowned one. The daemon's generic CLI launch writes the same pointer into a claude-cli, cursor-cli or other `*-cli` session's worktree at start and resume (`tddy-agent-launch`'s `cli_session_pointer`: the managed workflow's socket, session and repo dirs, and the notify session; removed when the agent exits and on delete, on this host and on an ssh target), and a headless conversation whose MCP slot is inline writes one in its conversation directory (`tddy-session-lifecycle`'s coding-agent launcher). It is how a `tddy-tools` the agent runs, from its shell or as its MCP server (which runs in the agent's cwd), reaches the session with no `TDDY_*` variable in its environment — see [tddy-tools session resolution](../../tddy-tools/docs/session-resolution.md). `find_session_pointer(start)` returns the nearest pointer at or above `start`; one that exists and does not parse is a `SessionPointerError`, never skipped for one further up. `TurnFiles::write(files, workdir)` writes a turn's files owner-only (`0600`, atomic), creating their directories; a file under the working directory is added to the repository's `info/exclude` before it is written (`exclude_from_git`; a working directory that is not a git checkout is refused), and one already there is refused rather than overwritten — it may be the repository's own. `write_session_pointer` replaces a stale pointer — one a crashed turn left, one whose owner is on another host or has exited, an ownerless one, or this session's own from its previous turn (the same socket) — and refuses one **held** for another session: a pointer naming a different socket whose owner is running on this host is not overwritten, and the turn fails with `SessionPointerHeld`'s message (the pointer path, the live owner's pid and host, and the socket it names), carried as `BackendError::InvocationFailed`. Dropping `TurnFiles` removes every file it wrote and the directories it created. Tests: `tests/session_pointer.rs`.
- **Codex sign-in** (`backend/codex.rs`): `spawn_codex_oauth_login(binary, session_dir)` runs `codex login` with browser OAuth (its `BROWSER` hook writes `codex_oauth_authorize.url` into the session directory), `CODEX_DEFAULT_CLI_BINARY` (`codex`), and the session-directory helpers (`write_codex_thread_id_file`, `CODEX_*_FILENAME`). No turn runs here: a `codex exec --json` turn is a `SpecHeadlessBackend` turn from `codex.yaml`.
- **acp_driver** (`backend/acp_driver.rs`, `client.rs`, `mapping.rs`, `permission.rs` — the permission types and `AllowOnce`, glob re-exported — `session.rs`, `worker.rs`; re-exported): the one ACP client every ACP backend runs on. `AcpDriver::spawn(AcpAgentCommand, Arc<dyn PermissionHandler>, Arc<dyn AcpAgentHooks>)` spawns the agent child (program, args, env, cwd; stdio piped, stderr discarded, `kill_on_drop`) on a dedicated `acp-driver` thread with a current-thread runtime and a `LocalSet` (the `ClientSideConnection` is `?Send`; only channels cross). A missing binary is an error from `spawn`; `initialize` runs once, on the first request. Requests: `open_session(OpenSession { cwd, resume, model, mcp_servers, meta })` — `session/load` for `resume`, else `session/new`, both with the stdio MCP servers and `meta` sent verbatim as `_meta` (where an adapter reads options the protocol has no field for, e.g. `claude-agent-acp`'s `disallowedTools`), then `session/set_model` for a requested model; a model the agent does not advertise (or any model, when it advertises none) is refused naming the offered ones and nothing is set. An open is bounded: `open_session` uses `SESSION_OPEN_DEADLINE` (120 s, covering the first request's `initialize` too) and `open_session_within(open, deadline)` takes one; an agent that has not answered by then is refused as `the ACP agent <program> did not open a session within <deadline>` and the driver is unusable afterwards (its child ends when it is dropped). `prompt(session_id, text, updates, progress)` returns `AcpTurnEnd { stop_reason, text }` and streams each `session/update` as an `AcpUpdate` (text, thought, tool call, tool-call update, plan; `ToolCallRecord` — a whole call with status and raw output — is never streamed by the agent, it is how a caller such as a coding subagent records a permission request and its answer on the same stream, and it is not progress) and as `ProgressEvent`s (message chunks → `TaskProgress`, `ToolCall` → `ToolUse`, a terminal `ToolCallUpdate` → `ToolResult`, plan → `TaskStarted`); one turn per session at a time, a second prompt is refused. `cancel(session_id)` sends `session/cancel` and the running turn ends `Cancelled`. `list_models()` reads a fresh session's models. Each request runs on its own local task, so a cancel reaches a running turn; each incoming message is polled once at once (`worker::run_or_spawn`) so a turn's last update is recorded before its prompt response. Dropping the last handle kills and reaps the child (`agent_pid()` is `None` after). `PermissionHandler::decide(PermissionRequest) -> PermissionDecision` answers `session/request_permission` verbatim (`PermissionRequest.kind` carries the tool call's ACP kind by its wire name — `edit`, `execute`, … — `None` when the agent named none); `AllowOnce` (the workflow backends' handler) picks the first `allow_once` option, else `Cancelled`. `AcpAgentHooks::on_session_error` may return `RetryOnce` after a failed `session/new` / `session/load` (`NoHooks` never does).
- **headless_driver** (`backend/headless_driver.rs`, `stream_json.rs`, `codex_jsonl.rs`, `oz_ndjson.rs`, `transcript.rs`; re-exported): a coding agent driven as a headless CLI behind the same conversation shape the ACP driver gives. `HeadlessCommand { env, cwd, model, permission_prompt_tool, disallowed_tools, profile, mcp_server, scratch_dir, renderer, turn_deadline }`; `HeadlessDriver::new(command)` runs **one CLI invocation per turn**, rendered from the agent's spec by `renderer` (see [Adapters](#adapters-adapters)): the prompt, the command's model, the kept session as `Resume`, the permission-prompt tool, withdrawn tools and MCP server (the renderer's own `tddy-tools --mcp` when `mcp_server` is `None`) as the slots' inputs, `profile` as a param, `cwd` as the workdir (the process's directory when unset) and `scratch_dir` as the scratch directory — the conversation's own directory, never the worktree, since the registration carries the agent's credential. A turn with no renderer or no scratch directory is refused: no argv is built by hand. `agent_id()` is the renderer's id. The turn's stdout is decoded by the transcript the spec's adapter makes (`StreamAdapter::transcript`; an adapter that makes none refuses the turn), its rendered files written owner-only first, and its environment is the command's `env` (a provider route's variables) then the spec's `headless.env` through `render_env`, `scratch_dir` standing for `{session_dir}`. The session/thread/conversation id the first turn's stream names is kept for the next. Each stream line becomes `AcpUpdate`s as it arrives (claude `tool_use` → `ToolCall`; codex `command_execution` items at turn end; oz `tool_call`/`tool_result` paired by tool name); the turn returns `AcpTurnEnd { stop_reason, text }` with the CLI's final text. A non-zero exit is an error carrying the last 20 stderr lines, read for at most `STDERR_GRACE`. The child spawns through `turn_process` (above) — its own process group, no inherited `TDDY_*` variable, registered as a `RunningGroup`; `cancel_turn` SIGKILLs the group and the turn ends `Cancelled`; dropping a turn's future or the driver kills an unreaped child; a turn that outlives `turn_deadline` (`DEFAULT_TURN_DEADLINE` when `None`) has its group killed and reaped and fails `"<agent> turn did not end within its <deadline> deadline; its process group was killed"`. One turn at a time per driver; a second is refused. **`ConversationDriver`** (`prompt_turn`, `cancel_turn`) is the trait a coding-agent session holds, implemented by `HeadlessDriver` and by `AcpConversation { driver: AcpDriver, session_id }`. Limits: cursor tool calls are not surfaced, prose is not streamed as `AcpUpdate::Text`, and a turn ends on stdout EOF (a grandchild holding stdout stalls it until its deadline; cancel does not). `HeadlessCommand::env` carries no tool-server variable: the `McpServerSpec { name, command, args, env, cwd }` a conversation is handed becomes the turn's `HeadlessMcpServer { …, cwd }`, and an agent whose MCP slot is inline (Codex) gets a server with no `env` and a `cwd` — the conversation directory, whose `.tddy/session.json` the server finds its session through (see `tddy-session-lifecycle`'s [coding-agent launcher](../../tddy-session-lifecycle/docs/coding-agent-launcher.md)).
- **ClaudeAcpBackend** (`acp.rs`): `bunx claude-agent-acp` (or `with_agent_path`, e.g. `tddy-acp-stub`) on the driver with `AllowOnce` and `NoHooks`. Fresh → `session/new`; `SessionMode::Resume(id)` → `session/load` of that id, so a resume survives a new backend. The request's `model` is applied unless a provider route is in force (the route's model stands).
- **CodexAcpBackend** (`codex_acp.rs`): `codex-acp` on the driver; the system prompt is merged into the prompt (`merge_codex_prompt`). Resume uses `load_session` with the id stored as `codex_thread_id` (the same file field a headless `codex` turn uses). `CodexLoginHooks` returns `RetryOnce` after running `codex login` (`spawn_codex_oauth_login`) on an auth-like session error when `session_dir` is set, so `codex_oauth_authorize.url` and headless OAuth flows match `--agent codex`; a failed login is the error the caller sees.
- **OpenCodeAcpBackend** (`opencode_acp.rs`): OpenCode as a tool-session agent — `opencode acp` on the driver, agent id `opencode`, binary `DEFAULT_CLI_BINARY` (`opencode`) or `with_agent_path`; `new_session` (or `load_session` on a resume), `prompt` with `merge_codex_prompt`. On a route (`with_provider_route`) the route's env carries the generated configuration inline in `OPENCODE_CONFIG_CONTENT` (`route.shape: inline_config`); no file is written, and the route's args are not passed (the generated configuration selects the model). Default and curated model `fireworks/kimi-k2` (`OPENCODE_DEFAULT_MODEL`); the selection question lists it seventh, as `OpenCode`.
- **StubBackend**: Stateful backend for demo and workflow tests. Uses `ToolExecutor` (InMemoryToolExecutor in tests, ProcessToolExecutor in tddy-demo). Magic catch-words: CLARIFY (returns questions), FAIL_PARSE (malformed response), FAIL_INVOKE (BackendError). Returns schema-valid structured responses per goal.
- **ToolExecutor**: Trait for submitting structured results. `InMemoryToolExecutor` stores via `store_submit_result` (tests and tddy-demo StubBackend). `ProcessToolExecutor` runs `tddy-tools submit` for real agents. `BackendInvokeTask` prefers `take_submit_result_for_goal` over stream parsing.
- **InvokeRequest/InvokeResponse**: Request and response types. InvokeRequest: prompt, system_prompt, goal (Plan/AcceptanceTests/Red/Green/Demo/Evaluate/Validate/Refactor/UpdateDocs), model, session (Option<SessionMode>), working_dir, debug, agent_output, inherit_stdin, extra_allowed_tools, conversation_output_path. SessionMode: Fresh(id) or Resume(id) — single type for session_id + mode. InvokeResponse: output, exit_code, session_id (Option), questions, stderr (Option — whatever the child left).
- **ClarificationQuestion**: Structured question type from AskUserQuestion tool events or `<clarification-questions>` text block (header, question, options, multi_select).
- **workflow_recipe_selection_question / recipe_cli_name_from_selection_label**: Single-select labels `TDD` → `tdd`, `Bugfix` → `bugfix` for presenter recipe switching after `/recipe` from the feature slash flow.
- **model_catalog**: Assembles the models an agent supports and the JSON contract that reports them — querying the underlying agent command where it can (cursor `--list-models`, ACP `available_models`) and falling back to a curated list. It sits beside the backends it enumerates; `tddy-tools list-models` is the clap surface over it and owns the `println!` and the exit code, because this crate is linked by the TUI and must not write to stdout.
- **Goal tool allowlists** (`plan_allowlist`, `green_allowlist`, …, passed as `--allowedTools`)
  live in `tddy_workflow_recipes::permissions`, beside the recipes that choose them.

## Adapters (`adapters`)

A coding agent's headless invocation is declared in its tool definition (`coding_agent.headless`, owned by `tddy-coding-agent-specs`); what stays Rust is the code that reads its output, registered here by name.

- **`StreamAdapter`** (`name`, `read_stream(reader, StreamSinks)`, `exit_ok(exit_code, &StreamResult, exit_ok_if_structured)`, `failure_detail(&StreamResult, stderr) -> String`, `transcript(Option<AcpUpdateSink>) -> Option<Box<dyn TurnTranscript>>`). `StreamSinks` carries the progress, raw-output, debug-line and conversation-line callbacks. `failure_detail` is what a failed workflow turn's error carries after its exit code: Claude's stream errors joined (else its stderr), Codex's last stream error (else a brief of its stderr) with `codex_openai_auth_remediation` after a blank line on an auth failure, Cursor's and Oz's stderr; empty when there is none. `transcript` is the conversation transcript a `HeadlessDriver` turn feeds its stdout to (`TurnTranscript::push_line`, then `finish(TurnEnding::{Cancelled, Exited { status, stderr }}) -> TurnFinished { session_id, result }`); every built-in adapter makes one.
- **`AdapterRegistry`**: `builtin()` registers `claude-stream-json` (`CLAUDE_STREAM_JSON`), `cursor-stream` (`CURSOR_STREAM`), `codex-jsonl` (`CODEX_JSONL`) and `oz-ndjson` (`OZ_NDJSON`); `get`, `contains`, `names`. Each wraps its parser (`stream::process_ndjson_stream`, `stream::cursor::process_cursor_stream`, `headless_driver/codex_jsonl.rs`, `headless_driver/oz_ndjson.rs`); Claude's and Cursor's transcripts are `headless_driver/stream_json.rs`, Codex's and Oz's their own modules. `LaunchAdapters::builtin()` adds the models adapter `cursor-models` (`CURSOR_MODELS`, over `parse_cursor_model_list`) beside `opencode-models`. Spec load refuses a name the registry does not hold, so a YAML-only headless agent naming a registered adapter runs with no Rust change.
- **`ClaudeStreamJson`** (`claude_stream_json.rs`) wraps `stream::process_ndjson_stream` unchanged. `exit_ok` is true for exit 0, or for a non-zero exit when the declaration allows it and the result text holds a `<structured-response`. Cursor's adapter checks its exit the same uniform way.
- **`HeadlessRenderer`** (`headless.rs`) is the port both headless drivers render through, since they cannot name `CodingAgentSpec` (that crate depends on this one). `agent_id`, `tool_server() -> Option<HeadlessMcpServer>`, `render(&HeadlessTurn) -> HeadlessInvocation { program, argv, env, files, adapter, exit_ok_if_structured }`. `HeadlessTurn` holds the prompt, model, session, permission mode, append-system-prompt file, allowed / denied tools, permission-prompt tool, MCP server, workdir, scratch dir, agent `params` and provider `route_args`. `tddy_coding_agent_specs::headless::SpecHeadlessRenderer` implements it. `write_rendered_files` writes `HeadlessInvocation::files` with mode 0600 before the spawn.
- **The headless protocol** (`headless.rs`): what a workflow turn of one agent runs with beyond its argv, read from its spec's `coding_agent.headless` fields and re-exported by `tddy_coding_agent_specs::headless`. `HeadlessProtocol { system_prompt: SystemPromptDelivery::{Flag, Prepend}, goal_params: GoalParams, approval_tool, workflow_mcp, route_model: RouteModel, fresh_session: FreshSession::{Caller, Agent}, scratch: ScratchDir::{SessionDir, Workdir} }`. `GoalParams { always, plan_mode, read_only_plan, accept_edits }::bind(&GoalHints)` binds the maps in that order, a later one overriding an earlier one's name: `plan_mode` for a goal in the agent's plan mode, `read_only_plan` for one that is also read-only, `accept_edits` for one that accepts edits. `RouteModel::{Kept, Replaced, ReplacedIfRouteHas { flag }}::model_for(model, route_args)` is the model a routed turn names. `EnvTemplate { session_dir, self_exe }` and `render_env(env, template)` render `headless.env`. `HeadlessModelListing { program, argv, adapter }` is a spec's model listing.
- **Consumers.** `SpecHeadlessBackend` renders every workflow turn and `HeadlessDriver` every conversation turn through the port; neither builds an argv by hand.

- **ACP hooks adapters** (`acp_hooks.rs`, `#agent-tools 11/12`): what an ACP agent's spec names in `coding_agent.acp.hooks_adapter`. `AcpHooksAdapter::prepare(AcpHooksLaunch) -> PreparedAcpHooks` gives the driver its `AcpAgentHooks` plus an `AcpOpenScope` that brackets each `open_session` (the request's session directory, its own failure). `AcpHooksAdapters::builtin()` registers `codex-acp-login` (`codex_acp_login.rs`: `codex login` with the resolved `codex` dep and one retry after an auth-like `session/new` / `session/load` error) (the `opencode-route-file` adapter was removed in `#agent-tools 29/32`: OpenCode's route is inline); `get`, `contains`, `names`. Spec load refuses a name the registry does not hold. `ClaudeAcpBackend::with_command`, `CodexAcpBackend::with_launch` and `OpenCodeAcpBackend::with_launch` take a rendered `AcpAgentCommand` (and the hooks and deps); `tddy_coder::acp_from_spec` builds them from the specs.

Tests: `src/adapters/*` unit tests (the registry, each adapter over a recorded stream against its parser, `exit_ok` both ways), `tests/headless_protocol_unit.rs` (the protocol types, `failure_detail` per adapter, every adapter's transcript) and `tests/headless_renderer_port.rs` (a fixture renderer drives both consumers).

## Stream (`stream`)

- **stream/claude.rs**: `process_ndjson_stream` — Claude Code CLI NDJSON parser (assistant, user, result, tool_use, task_started, task_progress). Tool_result content from user events is collected separately and merged into result_text only as a fallback when primary sources (assistant text, result event) lack a structured-response block.
- **stream/cursor.rs**: `process_cursor_stream` — Cursor agent NDJSON parser (assistant, tool_call, result; askUserQuestionToolCall/askQuestionToolCall).
- **StreamResult**: result_text, session_id, questions, raw_lines.
- **ProgressEvent**: ToolUse (carries `input_json` + `call_id`), ToolResult (`call_id`, `result_json`, `is_error`), TaskStarted, TaskProgress for real-time display. A `tool_use` followed by its `tool_result` emits a correlated `ToolUse` + `ToolResult` pair (shared `call_id`).
- **parse_clarification_questions_from_text**: Fallback when agent outputs `<clarification-questions>` block instead of AskUserQuestion tool.

Cursor's question-tool shapes: [cursor-ask-question-schema.md](cursor-ask-question-schema.md).

## Agent child environment (`agent_env`)

What an agent child starts from, as data the caller computes — never inherited. `agent_child_env(base, parent, launch)` returns the base set's variables of `parent` (names and `PREFIX_*` patterns, matched by `matches_env_pattern`), then `launch`'s variables; an inherited `TDDY_*` variable never passes (`TDDY_ENV_PREFIX`), a `TDDY_*` variable the launch sets on purpose does (today only Codex's `TDDY_CODEX_OAUTH_OUT`, an exception that expires with the Codex OAuth follow-up). `apply_agent_child_env(command, env)` is `Command::env_clear` then `envs`. The base set is a parameter, never a constant: `tddy_coding_agent_specs::AgentEnvBase::agent_env` adds the spec's `pass_env` and is what the daemon calls with `std::env::vars_os()`.

Every host site starts from exactly the env the daemon computed: the headless turns (`turn_process`), the model listing (`HeadlessModelListing.env`), the ACP worker (`AcpAgentCommand.env` is the whole environment of the agent, so a test that configures `tddy-acp-stub` hands it `TDDY_ACP_SCENARIO` and `TDDY_ACP_STUB_RECORD` there) and the conversation-id mint. Tests: `tests/agent_env_allow_list.rs` (each site plants `CLAUDE_CODE_CHILD_SESSION` and a `TDDY_*` in the parent and asserts the child sees neither), `agent_env/agent_env_tests.rs`.

## Spawn environment (`spawn_env`)

- **env_non_empty**: Reads an environment variable, returning `None` when it is unset **or blank** — whitespace included. Every `TDDY_*` variable in the workspace is exported by an outer process (a daemon spawning a jail, a shell wrapper, a systemd unit), and all three can export one empty without meaning to: a blank `TDDY_SOCKET` is not a socket path and a blank join token is not a token, so "set to nothing" and "unset" are the same claim and must read as the same value.
- **One spelling, deliberately**: the workspace had grown three of this rule, and two of them disagreed — one trimmed before testing for empty and one did not, so a LiveKit variable exported as `" "` configured a transport whose URL was one space. Callers that read a spawn variable use this function rather than declaring a fourth reading.

## Provider routes (`provider_route`)

What a harness process needs to run on a model-provider account instead of its vendor — pure data,
applied by the caller (`tddy-agent-launch` for a PTY, the backends in [Routed backends](#routed-backends-provider_route_file-backendrouted) for a tool session). Product view:
[provider accounts § Running a harness on an account](../../../docs/ft/daemon/provider-accounts.md#running-a-harness-on-an-account).

| Item | Role |
|---|---|
| `ProviderKind::{Anthropic, OpenaiResponses, OpenaiChat, Meta}`, `RouteShape::{Env, TomlArgs, JsonConfigFile, InlineConfig}` (`word()` gives the YAML word refusals name), `RoutedAgent.config_env`, `RouteSupport { providers, shape }` | a spec's `coding_agent.route.{providers, shape}` (`provider_route/support.rs`; `tddy-coding-agent-specs` re-exports them under its own paths, since it depends on this crate). Shapes are named after the body format they are: `env`, `toml_args` (`-c key=value` TOML overrides), `json_config_file`, `inline_config` (the JSON configuration in the variable `route.config_env` names). A removed word (`args`, `config_file`) is refused at parse naming its replacement. `RouteShape`'s `Default` is a parse default only |
| `RoutedAgent { id, product, support, key_env }` | what a route body knows of one agent, built from its spec by `tddy_coding_agent_specs::routed_agent`. `product` is the spec's `coding_agent.product` (or the id); `key_env` its `route.key_env` |
| `bodies_accept(shape) -> &[ProviderKind]` | the providers a body exists for: `env` → `[anthropic, meta]`, `toml_args` → `[openai_responses]`, `json_config_file` and `inline_config` → `[openai_responses, openai_chat]`. `tddy-coding-agent-specs/tests/route_body_drift_acceptance.rs` pins every built-in spec's providers against it |
| `RouteTarget { preset, endpoints: RouteEndpoints, api_key: RouteSecret, model }` | one account and the model every model choice is pinned to. `RouteEndpoints` holds the `anthropic_messages`, `openai_responses`, `openai_chat` roots |
| `RouteSecret` | a credential value whose `Debug` is `RouteSecret(<redacted>)`; `expose()` is for the one place that hands it to a child |
| `HarnessRoute { env, secret_env, files: Vec<RouteFile>, args }` | what the agent is launched with; the key is only ever in `secret_env` |
| `RouteRefusal` | agent-keyed, each variant carrying the agent id and product: `AgentCannotBeRouted` (a spec with no providers — Cursor, Warp — "<product> cannot be pointed at another provider; it always runs on its own vendor"), `ProtocolNotServed { needs }`, `PresetNotAccepted` (Meta only), `NotYetRoutable` (a declared pair no body serves, or a body missing its `key_env`: "<product> (<id>) cannot run on a provider account in this build yet"); `Display` is the sentence an operator reads |
| `agent_routable(agent)`, `route_supported(agent, preset, protocols)` | whether the agent can run on any account at all, and on this one, answered without building a route; `protocols` are the wire spellings `anthropic-messages`, `openai-responses`, `openai-chat` |
| `resolve_route(agent, target)` | the route, its body chosen by (shape, the first declared provider the account serves) — never by the agent's name (`provider_route/by_spec.rs`). `(env, anthropic)` (`anthropic_env_route`, Claude Code): `ANTHROPIC_BASE_URL` = the Anthropic Messages root, `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL` = the model; secret `ANTHROPIC_AUTH_TOKEN`; args `--model <model>`. `(env, meta)` (`key_env_route`, Muse Code): the key alone in the spec's `route.key_env` (`META_API_KEY`) — no env, file or argument, so the session keeps its own `--model`. `(toml_args, openai_responses)` (`toml_args_route`, Codex, in `provider_route/codex.rs`): secret in the spec's `route.key_env` (`CODEX_PROVIDER_KEY`); args `-c model_provider="tddy-route"`, `-c model_providers.tddy-route.{name,base_url,env_key=<key_env>,wire_api="responses"}` (`CODEX_ROUTE_PROVIDER_ID`), `-m <model>` — values are TOML basic strings, the key is never an argument; the provider's `name` is the preset label from a closed table (`meta`, `openai-compatible`) — a preset outside it is `NotYetRoutable`, and `tddy-agent-launch`'s `codex_declares_every_responses_preset_under_the_label_the_accounts_table_gives_it` ties the table to `tddy_accounts::presets()`. `(json_config_file, openai_responses \| openai_chat)` (`json_config_file_route`, a drop-in spec; no built-in declares it): files `[opencode.json]`, secret in the spec's `route.key_env`, args `--model tddy-route/<model>`. `(inline_config, openai_responses \| openai_chat)` (`inline_config_route`, OpenCode): env `[(<config_env>, <the same configuration>)]` — `OPENCODE_CONFIG_CONTENT`, no file — secret in `OPENCODE_PROVIDER_KEY`, args `--model tddy-route/<model>`; it also needs `config_env`, else `NotYetRoutable`. Every body but the Anthropic-env one needs `key_env` and refuses an agent without one (`NotYetRoutable`): no fallback variable, and no route variable is a `TDDY_*` name |
| `opencode_config_for(target, key_env) -> Option<RouteFile>` | the `opencode.json` declaring the account as provider `OPENCODE_ROUTE_PROVIDER_ID` (`tddy-route`) and selecting `target.model` on it: `@ai-sdk/openai` over the Responses root with `include: ["reasoning.encrypted_content"]` when the account serves Responses, `@ai-sdk/openai-compatible` over the Chat root otherwise; `apiKey` is `{env:<key_env>}`, never the key. `None` when the account serves neither — the wire is selected through a private `OpenAiWire`, so no input panics |
| `RouteChoice { BuiltIn, Account(id) }`, `RouteSources { session, agent_definition, user_default }`, `choose_route` | precedence: session over agent definition over the person's default; `BuiltIn` at a level overrides everything below it; `None` is the vendor |

## Routed backends (`provider_route_file`, `backend::routed`)

A tool session's route travels from the daemon to `tddy-coder` in a file, because the spawn's
environment allowlist carries no credential.

| Item | Role |
|---|---|
| `provider_route_file::{PROVIDER_ROUTE_FILENAME, route_to_json, route_from_json, load_route_file}` | `provider-route.json` in the session directory: `{env, secret_env, files, args}`, every field required, unknown fields refused. A parse error names the position, never the text. `load_route_file` reads the mode from the open file and refuses any group or other bit |
| `SpecBackend::with_provider_route(route) -> Result<Self, RouteRefusal>` | the one entry `tddy-coder` calls (through `build_spec_backend`); each transport's own, below. An agent whose spec has no `route` section (Cursor) is refused with n13's agent-keyed `RouteRefusal`; `tddy-coder` refuses a route for `stub` itself |
| `SpecAcpBackend::with_provider_route` | refused through `provider_route::by_spec::agent_routable` (a public module since `#agent-tools 16/19`) for a spec with no `route` section; else the route's env on the agent child, then the spec's hooks adapter prepares the command — `codex-acp-login` adds the route's `-c` overrides there. A driver already started is dropped |
| `SpecHeadlessBackend::with_provider_route` | the route's env and secret env on every turn's child, and its args as the turn's `route_args`; the request's model is dropped as the spec's `route_model` says — Claude's when the route's args carry `--model` (`replaced_if_route_has`), Codex's always (`replaced`, the route's `-m` names it). Refused for a spec with no `route` section |
| `ClaudeAcpBackend::with_provider_route` | the route's env on the agent child; its args are not passed (the agent reads its model from the env) |
| `CodexAcpBackend::with_provider_route` | `codex-acp` takes the same `-c` overrides, with `-m <model>` rewritten to `-c model="<model>"` (`codex_acp_route_args`, added by the `CodexAcpLogin` hooks adapter's `prepare`, so `SpecAcpBackend` and `CodexAcpBackend` route the same way); the key in the agent's env |
| `OpenCodeAcpBackend::with_provider_route` | the route's env (its configuration inline in `OPENCODE_CONFIG_CONTENT`) and secret env on the `opencode acp` child, no file written; its args (`--model tddy-route/<model>`) are not passed |

The three ACP backends start their driver, and so the agent, on the first command, not at
construction, so a route set after construction reaches the agent. Setting a route replaces a driver
that already started, and dropping the replaced driver ends its child. A failed spawn is not kept: the
next command spawns again.

Tests: `tests/provider_route_file.rs` (round-trip, owner-only load, a group-readable file refused);
`tddy-integration-tests/tests/tool_session_provider_route.rs` drives each backend against stub binaries that record
argv and env.

## CLI agents — no descriptor table

This crate holds no per-agent descriptor. Until the `#agent-tools` sweep (20/28, #828) a
`CliHarness` registry (`cli_harness`, with `cli_harness_muse` / `cli_harness_warp` and
`claude_argv`) answered per-session-type questions — label, binary and its env override, route
config env, argv, model source, context agent — from Rust. Every field had a YAML home, so the
table and its curated-model and context-glob companions are deleted: an agent's session type,
argv, models and globs are read from its spec in `tddy-coding-agent-specs`
(`CodingAgentSpec::{render_run_argv, argv_params, curated_models, model_listing_argv}`,
`coding_agent.context_globs`), and this crate receives them as values from its callers.
`SpecAcpBackend` runs every ACP agent from its spec's rendered `acp.command`; the bespoke
`ClaudeAcpBackend` / `CodexAcpBackend` / `OpenCodeAcpBackend` are deleted with the table.
Protocol adapters under `adapters` keep their protocol names — they are implementations a spec
selects by name, and own no metadata. See
[`tddy-coding-agent-specs` § The only home of agent metadata](../../tddy-coding-agent-specs/docs/coding-agent-specs.md#the-only-home-of-agent-metadata-the-sweep-agent-tools-2028).

## Schema (in `tddy-workflow-recipes`)

- **JSON Schema validation**: All schema logic lives in **`tddy_workflow_recipes::{schema, schema_manifest}`**, next to the `goals.json` and `generated/` tree it is generated from. Schemas are embedded via `include_dir`; no schema files are written to disk. `tddy-tools submit --goal <goal>` validates JSON against the embedded schema before relaying to tddy-coder, and `tddy-tools get-schema <goal>` outputs the schema for inspection — the binary parses the arguments and owns the exit codes, the library answers about schemas. On validation failure, `tddy-tools` returns errors with a tip to run `get-schema`. The `red` schema defines an optional `source_file` on each `markers[]` item (file path where the marker was placed); `packages/tddy-workflow-recipes/generated/tdd/red.schema.json` is the generated schema. See [json-schema.md](../../tddy-workflow-recipes/docs/json-schema.md).
- **ProcessToolExecutor**: Invokes `tddy-tools submit --goal <goal> --data '<json>'` with TDDY_SOCKET set. Neither this crate nor `tddy-core` has a schema module.
