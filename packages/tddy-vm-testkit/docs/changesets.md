- **2026-08-14** [Feature] **tddy-vm-testkit — build the workspace in one guest, assert against it in another** — the cgroups code is the least-tested code in the workspace and least-tested exactly where its claims are strongest: on macOS `tddy-sandbox-cgroups` compiles to an empty lib, so `spawn_plan` cannot even be compile-checked, and on Linux every function touching `/sys/fs/cgroup` is either never executed or exercised against a `tempfile::tempdir()` — which accepts any bytes, enforces no limit, and returns `ENOTEMPTY` forever where the kernel returns `EBUSY`, so scope removal's retry path and its success path had never run. New crate baking a chain off **one** on-disk cloud image supplied through the existing `TDDY_CLOUDINIT_BASE_IMAGE` knob (nothing is ever downloaded), cached under the repo's own `tmp/.tddy`: a shared `tddy-nix-base` layer carrying Nix + flakes and the `tddy`/`alice` accounts, and two children chained onto it — `tddy-builder` (9p-capable kernel, warmed dev shell) and `tddy-test-host` (stock `-cloud` kernel, no toolchain). The builder is on the critical path rather than an optimisation: `tddy-supervisor`, `tddy-daemon` and `tddy-sandbox-runner` must be Linux/aarch64 ELF and an Apple-Silicon host cannot emit them, so it mounts the working copy read-only over 9p and `tmp/.tddy/dist` **writable** (the first writable 9p share in the workspace — `NinePShare { writable: true }` had been supported by the argv builder since it was written but had no call site), runs `./release`, and hands the binaries back to a host that cannot compile them. The test host takes a fresh disposable overlay per run because inherited cgroup state would undermine the assertions, receives the binaries by **scp** — not 9p, because giving it the generic kernel would diverge the kernel under test from the one a real host runs — and installs them with the real `./install --systemd --headless`. `guest.rs` generalises `packages/tddy-vm/tests/common/mod.rs`, keeping its `Drop` force-kill guard: unlike a testcontainers-backed testkit nothing stops a QEMU on its own, so a panicking test would orphan an emulator still holding the forwarded port. `env_file.rs` reads the repo-root `.env` with `web-dev`'s exact semantics (never overriding an already-set var) rather than adding a `dotenv` dependency, and `layout.rs` resolves the repo root from `CARGO_MANIFEST_DIR` rather than `default_tddy_data_dir()`, whose CWD-relative `tmp/.tddy` would scatter caches into `packages/<pkg>/tmp/.tddy` under `cargo test`. Two traps pinned by tests: the AppArmor profile's basename *is* `tddy-daemon`, so flattening the install bundle naively would overwrite the daemon binary with a text file and the guest would install cleanly then fail later unable to exec its own daemon; and `livekit.api_secret` doubles as the session-token HMAC secret, so a guest daemon with the block absent answers `Unauthenticated` to every RPC with no fallback. A crashed bake can no longer publish a half-baked layer: `is_sealed_file` treats only a `0444` file as finished, replacing an `exists()` cache that would have reported an interrupted bake's leftover as prepared. Root `./run-vm-testkit` warms the image cache; `--status` reports what is cached. **The five production tests in `packages/tddy-e2e/tests/vm_cgroups_acceptance.rs` have never been run end to end** — their gating is verified, the multi-hour bake chain is not — and three of them drive `mkdir`/`rmdir`/`tee` from a guest shell, so they prove the kernel premises `tddy-sandbox-cgroups` was written against rather than executing its functions; the remaining gaps are recorded in `docs/dev/TODO.md` § VM image chaining and testkit.
