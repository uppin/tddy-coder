# 2026-08-13 — Stack-seed base session on `StartSession`, and `AddPlannedPr` names the node it appended

**Type:** Feature

`validate_stack_seed_base_session(sessions_base, recipe, base_session_id, project_repo_root)` refuses a `StartSessionRequest.pr_stack_base_session_id` (field 31) that cannot seed a stack **before** the session-type dispatch and before anything is created, so the new-session form can show the reason rather than navigating away from an orchestrator that came up unseeded: a recipe that does not resolve to `pr-stack` is `INVALID_ARGUMENT` (legacy aliases resolve and are accepted), `tddy_workflow_recipes::pr_stack::check_stack_seed_base` supplies the base-session rules *and their wording* with only the status code decided here, and the repository check is the RPC's own because only it knows which project was asked for — canonicalized roots, *at or under* rather than equality (`Changeset.repo_path` is the main repo for a `tddy-coder` session but the session's own worktree for a claude-cli / cursor-cli / workspace one), no `repo_path` refused since "could not tell" is not "same repository", project ids never compared because an id is registry-local, and a seeded start with an empty `project_id` refused rather than exempted. `SpawnOptions` / `SpawnRequest` thread the id to `--stack-seed-base-session` through the extracted `spawner::pr_stack_spawn_args(stack_parent, stack_seed_base_session) -> Vec<String>` (trims, drops blanks, and is assertable where an inline `cmd.arg` sequence is not — a flag silently not passed is the feature's failure mode). `add_planned_pr` also returns `AddPlannedPrResponse.node_id` from the `StackNode` it already had, so the client stops inferring the appended node by diffing a plan the orchestrator agent writes to concurrently.
