# 2026-08-15 — remote-git-repo-over-livekit

**Type:** Feature

`remote_git_service.rs` serves every project as a git remote: `Serve` admits a stream (token → OS user → project by id-then-name → closed pack-verb whitelist → concurrency slot) **before** spawning anything, then runs the real `git upload-pack`/`receive-pack` on **pipes** — never a PTY, whose line discipline, lossy replay ring and mode prologue each corrupt a packfile silently. The repository path comes only from the registry, so no `project_ref` reaches a directory; argv carries `--`; the child runs as the project user via the PTY path's own `wrap_argv_for_privilege_drop`, with an environment **built rather than inherited** (`setpriv` preserves env, which would hand a cross-uid child the daemon's `LIVEKIT_API_SECRET` and the wrong `HOME`). Output is bounded (8 frames × 32 KiB, under the chunk-framing threshold) so a large clone cannot become large RSS — measured to cost nothing, 150 MiB at 2.54 MiB/s either way, the wire being the limit. The child never outlives its connection: its **process group** is signalled on stream end, since `pack-objects` would otherwise hold the object database open. `auth.rs` gains `LiveKitTokenServiceImpl` (room-JWT mint: server-chosen room and `remote-git-<uuid>` identity) so a client needs no LiveKit credential, and `token.TokenService` gains authentication plus a refusal to mint any `daemon-*` identity.
