# 2026-07-26 — pr-stack-ux-recovery: the daemon finally holds a GitHub credential and reports honestly when it does not. New `github_token_store.rs::FileGitHubTokenStore` is rooted at the previously-unread `auth_storage` config path (`github-tokens.json`, `O_CREAT` mode `0600` plus an explicit `set_permissions`, dir `0700`; `put` serialised on a process-wide mutex across its read-modify-write

**Type:** Fix

two concurrent logins each read the same map and the second write dropped the first operator's token — and published via `github-tokens.json.tmp` + `fsync` + `rename`, because a truncated in-place write parses as an empty map and lost *every* operator's token with only a log line; `read_all` distinguishes `NotFound` from a real read failure, which is now logged, since an `EACCES` was the only clue an operator diagnosing "PR status unavailable" could have had). `auth.rs::build_auth_entries` returns `anyhow::Result` and **refuses to start** when a configured `auth_storage` fails `probe_writable` (create dir, write probe, remove) — retention is a hard login dependency, so an unwritable path fails every login one operator at a time for a fault entirely visible at boot; no fallback to a store-less service, and the probe runs for a stub provider too. New `github_pr_credentials::pr_lookup_for_caller(stub_mode, stored) -> PrLookup { Empty | Perform(token) | Unavailable(reason) }` plus `ConnectionServiceImpl::pr_status_for_caller`, which resolves the caller's token from their session-token login and returns a `PrStatusView` **value, never a `Status`** — an unresolvable `owner/repo` stays `exists = false` (a repo with no GitHub remote genuinely has no PRs), a stub/demo login short-circuits to an empty result (never *unavailable*), and both `.map_err(|e| Status::internal(..))?` sites are gone so `query_branch` keeps returning its session/worktree/remote legs when GitHub is unreachable. `query_branch` populates the new `remote` leg via `tddy_core::worktree::remote_branch_ref_sha`. New `effective_spawn_branch(intent, new_branch_name, selected_branch_to_work_on)` (`local_branch_name`-normalised selection under `work_on_selected_branch`, trimmed `new_branch_name` otherwise) feeds the **node-link** sites in both `stack_parent`-taking spawn paths, so a *resumed* spawn re-links its planned node instead of spawning another unlinked session on every click; `resolve_chain_base_ref` deliberately still keys on `new_branch_name`, since a resolved chain base would make worktree setup run a real `fetch_chain_pr_integration_base` for a resume that creates nothing. Tests: `tests/pr_lookup_credentials_acceptance.rs` 5, `tests/effective_spawn_branch_acceptance.rs` 6 (incl. a new-branch spawn ignoring the `selectedBranchToWorkOn` the dialog sends unconditionally — without it, "prefer whichever field is non-empty" passes every other case while being wrong).
