# 2026-08-19 — `ListSubagents` offers registry assistants, so what a picker is offered is what it can attach

**Type:** Bug Fix

the RPC read `<tddyhome>/agents/*.yaml` and nothing else, while `StartSession`, local attach and peer attach had all moved to `resolvable_agent_defs()` (YAML + registry assistants). An assistant created in Models & Agents was therefore *attachable by id but never advertised*: it appeared in no roster or opt-in picker on any host, and because a peer's defs are resolved through the peer's `ListSubagents`, an assistant on another host was not attachable at all — qualified id or not. `list_subagents` now answers from `resolvable_agent_defs()`, the same union an attach resolves against, so an offered id and an attachable id cannot drift apart. No projection change: `subagent_info` already renders any `SpecializedAgentDef`, so an assistant is advertised with its qualified id, label, model, tools and an empty `replaces`. The listing stays keyless (`agent_def_for_spawn` remains the only credential-carrying variant), and it can now **fail** where it always succeeded — deliberately, with no fallback to the YAML half, since a daemon whose registry is unreadable cannot honestly say what it can attach and a partial answer is exactly how this read as "no agents exist". Each daemon advertises its own assistants only, so both ends of a common room need the fix.
