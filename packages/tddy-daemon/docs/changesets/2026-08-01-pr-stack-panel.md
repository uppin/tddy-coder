# 2026-08-01 — **PR-stack panel

**Type:** Feature

base-sync and dirty legs on `QueryBranch`, plus `ReorderPlannedPr` and `PullBaseIntoBranch`** — `query_branch` gains a fifth leg (`base_sync`, given the request's new `base_branch`) and reports worktree dirtiness, both **non-erroring** like the existing four: an unnamed base, an unknown checkout, a probe failure or a `spawn_blocking` timeout all degrade that leg alone. New `base_sync_cache` keyed on `(repo_root, base_ref, base_sha, head_ref, head_sha)` — no TTL because the answer is a pure function of the commits, errors cached so an unanswerable repo is not re-probed twelve times a minute, capped with oldest-insert eviction; the ref *names* are in the key because the cached value carries them and two branches at the same commit would otherwise render each other's identity. Every git subprocess in the handler (session scan, worktree, remote, base sync) moved onto `spawn_blocking_with_timeout` — the panel polls once per rendered row every five seconds. Two new mutating handlers carry the standard prologue ending in `require_pr_stack_orchestrator`, with `validate_session_id_segment` before any path is built; `pull_base_into_branch` recomputes the resolution **uncached** afterwards so the row repaints without waiting for a tick, and degrades rather than failing if that recompute times out (the pull already mutated the repo). Tests: `planned_pr_mutation_rpc_acceptance` (9, mutation-tested against deleted guards), `base_sync_cache_unit` (9), `query_branch_resolution_acceptance` extended to 13. (tddy-daemon)
