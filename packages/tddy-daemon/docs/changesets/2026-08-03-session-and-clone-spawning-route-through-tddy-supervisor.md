# 2026-08-03 — session and clone spawning route through tddy-supervisor when one is configured

**Type:** Feature

`spawner::plan_session_child` is extracted as the single place that decides *what* to run (passwd resolution, session id, LiveKit room and identity, the child config, the grpc port, the whole argv), so `spawn_as_user` becomes only the fork and the supervised path sends the same plan to `SpawnSession`: the argv exists in one place and the two backends cannot drift. A supervised host forks no spawn worker at all, and every unsupervised arm is the pre-existing code unchanged. Startup is watched on the same schedule either way — the supervised one by polling `session_status`, because `waitpid` is not available to a non-parent. An unreachable supervisor **fails** the operation; there is deliberately no fallback, since spawning as the daemon user instead is exactly the regression the supervisor removes. `DaemonConfig` gains `supervisor: { socket_path }`, whose presence is the switch, and the client is connected per operation rather than held on `ConnectionServiceImpl` — which avoided a constructor signature used by ~40 test files and survives a supervisor restart under a long-lived daemon. Two gaps this makes visible and does not close: `SignalSession` calls `libc::kill` directly and will `EPERM` against another user's session (TERM/KILL map onto `stop_session`, `SIGINT` has no equivalent), and claude-cli/cursor-cli/PTY sessions still spawn from the daemon because `pty_runtime.rs` drops privilege via `setpriv`. Tests: 446. (tddy-daemon)
