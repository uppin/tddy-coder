# 2026-07-30 — **session-branch-conflict

**Type:** Feature

`StartSession` refuses a new branch another session already owns instead of silently suffixing it `-1`** — new `branch_owner::find_session_owning_branch(sessions_base, branch)` holds the single ownership rule (prefer active, tie-break most recent `updated_at`, skip unreadable changesets), lifted out of `query_branch`'s inline closure so the RPC guard, `QueryBranch` (which keeps its `require_pr_stack_orchestrator` gate) and the Telegram spawn flow cannot drift. New `owned_branch_conflict` is called from `start_session` after peer routing and before the session-type dispatch — one check for `tool`/`claude-cli`/`cursor-cli`/`workspace`, and nothing exists yet when it fires (no session dir, changeset, branch, worktree or remote push). Opt-in via `StartSessionRequest.on_branch_conflict` (field 30: `""` suffixes as before, `"reject"` refuses), answered as `StartSessionResponse.branch_conflict` (field 5, `BranchConflict { branch, BranchSession owner, suggested_branch_name }`) with an empty `session_id` — a response field, not an error, because `tddy_rpc::Status` has no details channel and `StartSession` crosses hosts over LiveKit. Fires only for an explicit `new_branch_from_base` with a non-empty `new_branch_name`; `work_on_selected_branch` is never refused, and a branch no session owns still suffixes. Telegram carries the same check in `handle_telegram_branch_callback` (claude-cli derivation only) with a three-button `tbc:` inline keyboard (`sw` enters the owning session, `na` rewrites to `WorkOnSelectedBranch`, `sg` takes the suggested name), wired into `telegram_bot.rs`. Tests: `session_branch_conflict_acceptance` 9, `branch_owner_unit` 5, `telegram_branch_conflict_acceptance` 7; `clippy --all-targets -- -D warnings` clean.
