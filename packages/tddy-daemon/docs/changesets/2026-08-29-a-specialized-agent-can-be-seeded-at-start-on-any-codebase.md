# 2026-08-29 — a specialized agent can be seeded at start on any codebase placement

**Type:** Feature

`remote_agent_at_start_unsupported` and the split path's `specialized_agents` / `semantic_index` refusals are deleted, and a seed becomes the same operation an attach is, performed before the spawn. `seeded_roster_records` resolves each reference through the attach path's `roster_record_for` (bare name → this daemon, qualified id → the daemon it names, over the common room); `seed_session_agent_roster` claims a clone for every agent not co-located with the authoritative worktree and writes the entry, unwinding everything it got through on any failure. The three **co-located** launch paths (`start_sandboxed_claude_cli_session`, `start_sandboxed_cursor_cli_session`, `cursor_cli_spawn::spawn_cursor_cli_session_inner`) cannot write a roster entry at that point — a co-located start writes `.session.yaml` only once the agent has a pid — so `claim_co_located_seed_clones` claims the same clones, stamps each record's `codebase_session_id`, and hands back a `SeededCloneGuard` that releases them on `Drop` unless `keep()` is called after the metadata write, which covers every `?` in between without restructuring three launch paths. The facts a seed needs are **passed rather than read back**: `SeedCodebase::of_a_starting_session(session_dir, worktree_root, project_id, enforces_withdrawal)` — the three file reads the old refusal rested on were exactly these, and the start already held them. `SeededAgentClones` is a trait for the same reason `SessionRoomHost` is one: the cursor-cli spawn is a free function. Ordering is load-bearing — a spawn's `--allowedTools`/`--disallowedTools` are fixed at launch, so a seeded agent's withdrawal is real at launch rather than at the next resume. `semantic_index` on a split is forwarded to the codebase host (`workspace_start_request` → `index_workspace_worktree`). ⚠️ Behaviour change: `refuse_unenforceable_withdrawal` now runs on the co-located paths too, so a seeded agent declaring `replaces` is refused on an unsandboxed cursor-cli start instead of being accepted and silently unenforced — the rule `AttachSessionAgent` already applied. Pinned by `seeds_a_peers_agent_onto_a_session_whose_codebase_is_here` (two real daemons, through `StartSession` itself).
