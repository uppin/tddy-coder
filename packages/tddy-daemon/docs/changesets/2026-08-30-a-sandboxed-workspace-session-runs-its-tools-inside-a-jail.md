# 2026-08-30 — a sandboxed `workspace` session runs its tools inside a jail on the host holding the checkout

**Type:** Feature

`sandbox = true` confined the *agent* and let the host run the tools it asked for, which is sound only while the agent's jail and the checkout are on the same daemon; on a split placement the jail is on one host and the repository on another, so `run_exec_tool_locally` ran every tool on the codebase host's bare filesystem and `StartSession` refused `sandbox` with `codebase_daemon_instance_id` because the flag had nothing to mean there. `session_type: "workspace"` now accepts and persists it, and the daemon provisions a per-session jail at `<session_dir>/sandbox` holding the worktree read-write and nothing else of the host. One branch in `run_exec_tool_locally` covers all three callers — `ExecuteTool`, `StreamExecuteTool` and a roster agent's own loop through `local_agent_codebase_access` — because all three already funnel through it. A session recorded as sandboxed for which this daemon holds no jail (a restart) is **refused**, not served from the bare host, so the no-fallback rule holds past the life of the process that built the jail; an unsupported platform or a jail that will not provision is `failed_precondition` with the session unwound. Indexing still runs on the host worktree before the jail exists. `DeleteSession` stops the jail — the registry was the only thing holding its handle and nothing removed from it, so a jailed runner outlived its own deleted checkout for the daemon's life. ⚠️ **Sandboxed `claude-cli` and `cursor-cli` sessions are unverified end-to-end** against the narrowed profile they now share: their four suites fail on this machine on a pre-existing `self_arc called before set_self_handle` panic, before any jail spawns.
