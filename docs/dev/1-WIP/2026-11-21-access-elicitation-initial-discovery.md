## Combined conclusions

A "working orchestrator" is mostly assembly: several pieces already exist on master — session messages, watches, `tddy-tools monitor`, idle wake, turn delivery by terminal paste, `ClaimSessionTerminal`, and `StartSession` attachments by reference. The gaps, by requirement:

| Req | Gap | Seam |
|---|---|---|
| 1 read reach | Daemon Read/Grep/Glob are confined to the caller's own worktree (`contain_path`); there is no list of read roots, and no reach into other projects, agent homes or chat files | `tddy-tool-engine` `contain_path`/`tool_read`, `tddy-daemon-rpc` `role_guard.rs`, `project_home/caller.rs` |
| 2, 4 elicitation | No request-access tool, no grant store, and no pane prompt to answer one; writes are refused unconditionally for orchestrator roles | `role_guard.rs`, `tddy-session-activity` (pending-question model, `answers.rs`), `activity.proto` notification kinds, `tddy-session-web` |
| 3 session files | No tool writes an attachment; the orchestrator cannot write at all | `tddy-session-files` `session_attachments.rs`, `start_session_args.rs` |
| 5 freshness | Home is fast-forwarded only at start and resume; nothing reports the base a start was cut from or how stale it is; nothing watches the remote trunk | `tddy-worktree-service` `home_worktree.rs`, `tddy-git` `remote.rs`, `start_ledger.rs`, `tddy-github` + `tddy-host-service` `github_cli.rs`, `tddy-projects` `local_gh` |
| 6 LSP | Orchestrators get no `Lsp*` tools; the root is always the caller's own worktree; the index daemon has no unload-root RPC | `tddy-lsp-executor`, `tddy-index-daemon` proto, `role_guard.rs`, `project_home_launch.rs` |
| 7 prompt | `project_home_prompt.md` is 44 lines, written for main; it does not mention watches, messages, turn control, lifecycle or stack tools | `tddy-agent-launch` `project_home_prompt.md` |
| 8 back channel | Children get no guidance naming their orchestrator; targets (Coder/SSH) have no tddy-tools and `hooks.log` carries no message line | `tddy-agent-launch` (guidance, `remote_hook_follower.rs`), `tddy-core` `remote_hook_command`, `tddy-session-activity` `session_messages.rs` |
| 9 delivery | Only Claude declares `turn_input`; there is no native Claude↔Claude route and no per-child route choice | `tddy-coding-agent-specs`, `project_home/turn.rs` |
| 10 claim release | No release anywhere; leases are never forgotten | `tddy-terminal-rpc`, `tddy-cli-sessions` `control_lease.rs`, `home_terminal_leases.rs` |

Trunk polling pattern (chosen with the developer): read the repository `events` feed conditionally with an ETag, so a 304 is free and changes nothing. Honour `X-Poll-Interval` (default 60 s) and back off 60 s after an error. Run a catch-up sweep at start and every 15 min, for events the feed misses. Through `gh api -i`, a 304 exits non-zero and must be read as success. tddy's GitHub transport per project: `ProjectRecord.local_gh` (`packages/tddy-projects/src/project_storage.rs:50`) means the host's `gh` CLI (`packages/tddy-host-service/src/github_cli.rs`); otherwise a vault GitHub account is used through REST (`packages/tddy-github/src/github_rest_common.rs`).

Base: this stack sits on `#target-parity` 7/7 (#975, `feature/target-parity/target-worktree-stats`). That stack adds the answer file, the waiting hook on a target, the catch-all PreToolUse, and grows `remote_hook_follower.rs` to 511 lines; the split of that file is reserved for `#target-parity`'s sweep.
