# 2026-08-29 — a long subagent turn stops holding the main agent's only tool call

**Type:** Feature

`subagent_prompt` blocked until the subagent yielded, which is right for a discovery question a 7B model answers in seconds and wrong for what the roster made addressable: a full coding agent on another host, whose turn is measured in minutes. The main agent has one call in flight and no way to abandon it, so a long turn is indistinguishable from a hung one — and any client-side deadline along the path (Claude Code's own tool timeout, an MCP transport, the LiveKit RPC engine) ends the **call** while the turn keeps running, so the work completes and the answer is unreachable with nothing saying so. The fix bounds the **wait**, not the turn: a prompt blocks for at most `graceMs` (default 25 s) and, if the turn is still running, returns `{responseId, pending: true}` **without cancelling it**, to be collected by the new **`subagent_await`** `{responseId, timeoutMs?}` — the same outcome shape when ready, `pending` again when not. The dual shape is deliberate over always-async: a single shape would be tidier and would break every existing caller of the fast path and cost every discovery question a second round trip, so a turn that yields inside the grace period returns exactly what it returns today, distinguished only by a key it never carries. `graceMs` is per call rather than an environment knob because a workflow step waiting on a coding agent and a discovery question mid-edit want different numbers from the same process. What made this more than a wrapper was the locking: the prompt tool held the **process-wide** session table across the turn, so a long turn already blocked `subagent_list` and the `subagent_cancel` that would have ended it. The table became a registry the tools take and release; each conversation's session moved behind its own fair `tokio::sync::Mutex`, which **is** the queue (a prompt arriving mid-turn runs after it, against the history it leaves, because a conversation's history is one sequence); and `SubagentConversation` took over its own `model`/`usage`, refreshed at each turn's end, so a listing answers mid-turn with the totals as of the last *completed* turn rather than a partially-billed one. Cancelling resolves rather than orphans — `subagent_cancel`, and a detach that cancels a conversation underneath a prompt, answer every pending turn of it, because an await for a turn nobody will finish has to return. **No daemon change**: a remote agent's turn already arrives as a `PromptAgentConversation` server stream consumed to completion, and the background task drives exactly that call — nothing about the wire, the frame contract or the truncation rule moved, only which task awaits it. Known and deliberate: a conversation cancelled with a turn genuinely mid-flight loses that turn's token accounting (the task is aborted before its table update, as an abandoned synchronous turn always was); a failed turn records the tokens it spent but does not increment `turns`, having added nothing to the history; collected results are never freed, since dropping one drops an answer that was paid for; and the `TODO(livekit-rpc-deadline)` on the client stream stands — a background turn against a dead daemon still hangs, it just no longer hangs the caller.
