# 2026-08-29 — a peer agent session's row says what its agent is doing

**Type:** Feature

a `SessionEntry` said what a session *is* and, through the bare hook word `activity_status`, that its agent was inside *a* tool call — never which one. An operator running an orchestrator with five peer agent sessions could not tell a stuck agent from a working one without attaching to five terminals. `SessionEntry` gains **`agent_status`** and **`last_activity`**, reusing the roster's own `SessionAgentStatus` / `SessionAgentActivity` verbatim so one badge renders a roster agent and a peer session alike, and riding `ListSessions` rather than a second stream. Neither is a new *source*: both are **inferred** by tailing what the session already writes — the resolved transcript `acp_replay::read_session_transcript` serves `StreamAcpReplay` from (`acp-transcript.jsonl` merged with `agent-activity.jsonl`, so a daemon-hosted session that writes only the latter is covered) seeds the newest signal once, and the daemon's existing per-session `AgentActivityHub` broadcast keeps it current. Two properties carry the design. **One mapper**: a live activity record is mapped *through* `frame_for_agent_activity` and into the same function a replayed frame goes through, because a second mapper would let a row and its replay word the same call differently, surfacing as a session that rewords its own status when the daemon restarts. **Subscribe before seeding**: `ensure_tailing` claims, subscribes and spawns before it reads the file, and the seed writes only when nothing has been observed — reversing the two would drop exactly the record that lands during the read. Five rules decide the status, of which two are not obvious: a hook word of `Done`/`Ended` **outranks a tool call left in flight** (a `running` row whose terminal record never arrived would otherwise pin the badge at EXECUTING_TOOL for the session's life), and otherwise a call in flight outranks the hook's `Running`, being strictly more precise and the only source of the call's name. Nothing observed and no hook word stays UNSPECIFIED — *"this daemon has nothing to say"*, never "idle" — which is also what every session type that runs no agent reports, since only `claude-cli` and `cursor-cli` are tailed (the gate `ReportSessionStatus` already applies; a `workspace` session would spend a subscription and a file read to conclude UNSPECIFIED). Nothing is persisted, and `DeleteSession` forgets, so the consumer exits instead of holding a subscription for the daemon's life. `activity_status` is untouched and keeps its own field: it is the *reported* hook word, and this is an inference built partly on top of it. Known and deliberate: a seed that fails to read is not retried (the session is claimed before the read; un-claiming would spawn a second consumer on retry), the seed is read once per daemon lifetime per session, there is no cross-daemon inference, and `WAITING_FOR_INPUT` still has no producer but the hook word. ⚠️ Recorded in `docs/dev/TODO.md` en route: `session_list_status_from_session_dir` returns early for `cursor-cli` before reading `changeset.yaml`, so a cursor session spawned under a stack parent never carries its `orchestrator_session_id` and never appears as a peer in the web at all.
