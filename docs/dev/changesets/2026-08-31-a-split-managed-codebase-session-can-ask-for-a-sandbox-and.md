# 2026-08-31 — a split managed-codebase session can ask for a sandbox, and it confines the codebase half

**Type:** Feature

`StartSession` refused `sandbox = true` together with `codebase_daemon_instance_id` (a split placement) with `invalid_argument`, on the premise that a sandboxed spawn resolves its worktree on the daemon running the agent — which a split session has no repository on. That premise predates the workspace tool sandbox (#427): `sandbox = true` on a `workspace` session now provisions a per-session jail on the host holding the checkout and routes `ExecuteTool`/`StreamExecuteTool` through it, so the flag confines the thing that touches the repository, and on a split placement that thing lives on the codebase host. The refusal is removed; the semantics are **inverted by placement**, not by the flag — co-located sandbox is unchanged (it still jails the agent on this daemon). On a split placement the agent half stays **unsandboxed** (`sandbox: None` metadata, the existing `spawn_split_agent` path), and the codebase half is **sandboxed** (`sandbox: Some(true)`, the workspace session on B via the already-landed `workspace-tool-sandbox` path). No new wiring was needed on the forward path: `workspace_start_request` already carried `sandbox` via `..req.clone()`, and the codebase host's workspace start already persists and provisions from it — the entire production change is the deletion of the five-line `invalid_argument` block in `start_split_claude_cli_session`. Validation gates for split+sandbox are the same as split today (`managed_codebase`, `claude-cli`, eligible codebase daemon); `recipe` is still refused on a split placement. ⚠️ **Two downstream PRs own what this one does not**: `split-sandbox-resume` re-provisions the jail from persisted `sandbox: Some(true)` after a stop or daemon restart, and `web-split-sandbox-toggle` removes the `isSplitCodebase` guard that still withdraws the Sandbox control on the form — so the daemon admits a combination the UI does not yet offer.
