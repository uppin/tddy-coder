# 2026-07-27 — **unified-worktree-base-resolution

**Type:** Fix

chain base resolution moves to tddy-core; cursor-cli PR-stack children base off the planned node, not origin/master** — `resolve_chain_base_ref` and its helpers `parent_is_pr_stack_orchestrator` / `pr_stack_node_for_spawn` move from `tddy-daemon::connection_service` to `tddy-core::session_chain` (single source of truth), and a new `resolve_chain_base_for_session_spawn` encodes the spawn-time precedence: a runtime `stack_parent` wins over a persisted `worktree_integration_base_ref`, which wins over the default base. The cursor-cli spawn paths (sandboxed and non-sandboxed) — which hardcoded `None` for the chain base and dropped `stack_parent` at the dispatch site — now thread `stack_parent` through, set `Changeset.orchestrator_session_id`, and resolve the chain base via the shared function, so a PR-stack child bases off its planned node's effective base (`Stack::base_ref_for_spawn`) instead of `origin/master`. Claude CLI and Telegram route through the same resolver; the daemon keeps a thin `resolve_chain_base_ref_status` wrapper mapping `String` → `Status::failed_precondition`. `tddy-workflow-recipes::ensure_worktree_for_session` keeps its direct read of `worktree_integration_base_ref` (no `stack_parent` and no project `sessions_base` on that path, so the precedence rule reduces to that field). Tests: `tddy-core/tests/unified_chain_base_resolution.rs` 6 (resolver contract + precedence), `tddy-daemon/tests/unified_worktree_base_acceptance.rs` 3 (cursor-cli + claude-cli PR-stack child + no-stack default); `clippy -p tddy-core -p tddy-daemon -p tddy-workflow-recipes --tests -D warnings` + `cargo fmt --check` clean.
