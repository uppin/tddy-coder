# 2026-08-02 — **daemon-spawned-tddy-host-vm

**Type:** Feature

the daemon can bake a Debian cloud image into a VM that *is* a tddy host, and boot it** — two additive methods on `vm.VmService`: `BuildTddyHostImage` (server-streaming) bakes a prepared base whose guest has `tddy-daemon`/`tddy-coder`/`tddy-tools` built from the operator's own working copy — reaching the guest over a read-only virtio-9p share, so no git URL and no credentials — and installed as a systemd service with the LiveKit common room configured; `CreateVmFromPreparedBase` then makes cheap per-VM overlays from it. Project cloning and session start need **no new code**: the guest self-announces on the common room and the existing `CreateProject`/`StartSession` flow targets it by `daemon_instance_id`. Getting there meant fixing a launcher that could not boot anything on an Apple Silicon host — `qemu-system-x86_64`, `-m 512M`, no `-smp`, no accelerator, no firmware, and `RunPolicy`'s persisted memory/cpus ignored — so `tddy-vm` gained arch/accel/UEFI/resource/per-VM-SSH-key support, a **pure**-core serial-console driver (`serial_shell`, ported from `~/Code/makers-lt`'s `@wix/shell-utils`) that can log in and run commands over UART before sshd or networking exist, and the cloud-init recipe itself. Three findings only a real guest could produce: Debian's *cloud* kernel ships **no 9p modules at all** (installing the generic flavour is insufficient — GRUB keeps preferring cloud, so the recipe purges it and reboots, guarded on `uname -r`); cloud-init frames its host-key banner in rows of `#`, which the prompt matcher took for a shell prompt and so typed commands at a getty; and `ttyAMA0` interleaves `printk` into command output, which is why the acceptance helpers now `dmesg -n 1` after login. PR-wrap validation then caught four criticals and two blockers, all fixed, of which two would have made the feature unusable as merged: the kernel step's `systemctl reboot` was incompatible with the bake's `-no-reboot` (QEMU *exits* on guest reset, so the bake could never succeed — `-no-reboot` dropped), and a failed kernel install exited 0 and let a prepared base with no tddy in it be sealed and reported as a successful bake (status now propagates; `runcmd` opens with `set -e`). Also fixed: a silent fallback in `registry.rs` that booted a VM as root with no key when a manifest was unreadable; the bake retaining plaintext LiveKit secrets and tens of GB on disk; a symlink-attackable `/tmp` log; LiveKit credentials written into the guest world-readable; missing path-traversal validation on RPC-supplied library names; and a `StartDemoVm` regression to an existing feature. Tests: **167** in `tddy-vm`, **19** in the daemon VM suites, **6/6 real-boot acceptance tests** against `debian-12-genericcloud-arm64` (~327 s, zero leaked VMs); `clippy -D warnings` and `cargo fmt` clean for the touched packages. **Known limitations, both accepted deliberately:** the hours-long bake has never been run end to end (every prerequisite is verified against a real guest, but the in-guest Nix/`./release`/`./install` tail is not — run procedure in the feature doc), and `packages/tddy-web/src/gen/vm_pb.ts` is not regenerated (`bun install` wedged; no web code consumes the new messages, so nothing is broken).
