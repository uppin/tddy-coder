# 2026-08-30 — a planned PR started on another host stops disappearing from its own stack

**Type:** Bug Fix + Feature

starting a pr-stack node's session on a daemon other than its orchestrator's made the PR-Stack row lose the node entirely: it went back to offering **Start session** for work already running, every descendant became unspawnable, and its GitHub PR never appeared. Three independent false negatives produced that one symptom, and each is fixed at its own layer. The node link was written on the *spawning* daemon's sessions tree, where the orchestrator does not exist, so the write was silently skipped — it is now the peer-routed `LinkStackNode` RPC, the write half of the `ResolveStackBase` read that was already routed for exactly the same reason, keyed on an explicit `StartSessionRequest.stack_node_id = 37` the surface that rendered the button sends rather than re-derived from `new_branch_name`, which the operator can edit in the create dialog. `ResolveStackBaseRequest.stack_node_id = 6` carries the same key on the base leg, without which a renamed branch skips the *ordering* gate altogether — `pr_stack_node_for_spawn` finds no node, `resolve_chain_base_ref` answers `Ok(None)`, and the child is cut from `origin/<default>` for a node whose non-merged parent owns no branch, silently, under a healthy status chip. A claude-cli session published no LiveKit participant metadata at all, so its synthesized cross-host drawer row carried neither of the two keys every PR-stack join uses; the `session` block moves to `tddy_core::session_participant_metadata` (the merge into participant metadata is **shallow**, so two publishers of a partial object erase each other), gains `session_id`/`orchestrator_session_id`/`stack_node_id`/`branch`, and the daemon now publishes it for claude-cli sessions on a 30 s republish timer — a dropped `set_metadata` or a room rejoin would otherwise lose the association permanently. The view joins on its own `StackChildSession` type built from the session list plus the metadata map the drawer already keeps, so no `SessionEntry` field was added and the join is not coupled to the `ListSessions` shape. Two adjacent gaps close with it: a node owning no branch is now polled on its `branch_suggestion` with **only** the host-independent `pr` leg read (any other leg would let a planned name feed base resolution, the exact failure D1 exists to prevent), and Start session is **never disabled** — two of its three blockers are derivable from legs that can only see one host, so a gate that cannot see half the fleet advises (warning colour, alert icon, tooltip naming every blocker) while the daemon's own gate refuses, with the real reason. A cursor-cli child recorded nothing on its planned node on *any* host — a pre-existing gap closed here. Four review passes found two serious defects: a blocked node's spawn sent an explicit `selected_integration_base_ref`, which `select_worktree_base_ref` gives precedence over the chain base, so the spawn most needing the ordering gate was the one bypassing it (the web now sends no base for a blocked node, and lookup prefers the node id); and both link sites recorded the *requested* branch while `create_worktree_with_retry` appends `-1` on collision, so a node could advertise `feature/x` while its child worked `feature/x-1` (the branch is now read back off the child's changeset). ⚠️ **Both hosts must be upgraded together.** A peer on an older daemon serves no `LinkStackNode`, `forward_to_peer` returns an unknown-method error, D36 logs it rather than failing the spawn, and the pair falls back to pre-fix behaviour — not a crash, but the node keeps no branch and its descendants stay unspawnable; an older peer likewise ignores `ResolveStackBaseRequest.stack_node_id` and loses the ordering gate for a renamed branch. Five residuals are logged rather than hidden, in [TODO.md](../TODO.md) and the PRD's *What is deliberately not fixed here*: the `worktree` and `remote` legs stay local-only, `resolveRepointTarget` still skips a parent invisible from this host, the daemon-side block carries static fields only, a **sandboxed** claude-cli session joins no room and so publishes nothing, and a sandboxed cursor-cli session still records nothing on its node.
