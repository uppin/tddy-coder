# 2026-08-14 — **vm-cgroups-testkit

**Type:** Feature

a VM that builds the workspace, a VM that runs it, and image chaining that stopped being a lie** — the cgroups code was least-tested exactly where its claims were strongest: on macOS `tddy-sandbox-cgroups` compiles to an empty lib, and on Linux every function touching `/sys/fs/cgroup` was either never executed by a test or exercised against a `tempfile::tempdir()` — which accepts any bytes, enforces no limit, and returns `ENOTEMPTY` forever where the kernel returns `EBUSY`, so scope removal's retry and success paths had **never run**; the two jail tests that could have run for real self-skipped *green*. New **tddy-vm-testkit** bakes a chain off one on-disk cloud image (`TDDY_CLOUDINIT_BASE_IMAGE`; nothing downloaded) into the repo's `tmp/.tddy`: a shared `tddy-nix-base`, then `tddy-builder` and `tddy-test-host` chained onto it. The builder is a hard requirement rather than an optimisation — the supervised stack must be Linux/aarch64 ELF and an Apple-Silicon host cannot emit it — so it mounts the working copy read-only over 9p and `dist/` **writable** (the workspace's first writable 9p share), runs `./release`, and hands the binaries back; the test host takes a fresh overlay per run, receives them by **scp** rather than 9p so it can keep Debian's stock `-cloud` kernel, and installs them with the real `./install --systemd --headless`. Building it exposed that the existing chaining flattened: `cloud_init.rs` ran `base_convert_argv` (`convert -f qcow2 -O qcow2`) on every bake, so each "layer" was a full copy of everything beneath it, and copying an overlay into a scratch subdirectory stranded its relative backing reference. Fixed at the root for all callers — the pristine import is now the only full image, every layer is a `qemu-img create -b` delta created at its final path (a relative backing reference resolves against the referencing image's directory, so a created-then-moved overlay points at nothing), and `promote_prepared_base_pair` is deleted along with the flattener. `/pr-wrap` then found three criticals, each fixed red-first: re-baking any layer died `EACCES` on the sealed `0444` overlay; a **relative** library root made `tddy-vm-build cloud-init` fail 100% of the time with no flags; and `create_vm`'s per-VM keypair was never injected into the guest, so with `BatchMode=yes` + `IdentitiesOnly=yes` no `ssh`/`scp` into a library VM could authenticate — after a multi-hour bake. Guarded by `no_disk_flattening_acceptance.rs`, which scans production sources for a qcow2-source convert and allowlists only the two legitimate raw-to-qcow2 normalisers. Tests: 208 across the VM packages, 0 failed; the 14 new chaining tests run in the default suite because they drive `qemu-img` without booting anything. **Known limitations, deliberate:** the five production tests in `packages/tddy-e2e/tests/vm_cgroups_acceptance.rs` have never been run end to end (gating verified, bake chain not), and three of them drive `mkdir`/`rmdir`/`tee` from a guest shell — proving the kernel premises `tddy-sandbox-cgroups` was written against rather than executing its functions, which needs the gRPC path listed in `docs/dev/TODO.md` § VM image chaining and testkit, alongside `VmManager::start`'s identical seed gap and the absence of any recorded parent identity per layer.
