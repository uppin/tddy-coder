# 2026-07-02 — Cloud-init image build with image-chaining (`tddy-vm-build cloud-init`)

**Type:** Feature

new `tddy_vm::cloud_init` module: immutable-base + qcow2 delta-overlay chaining (`qemu-img create -b` with a relative backing-file basename) and NoCloud cloud-init seed generation (`xorriso -as mkisofs` cidata ISO); async `build_cloud_init_image` orchestrator copies the caller's base image, converts it to an immutable base, resolves/generates an SSH keypair, renders and seeds NoCloud user-data/meta-data (SSH-key substitution, a DHCP netplan default, a `cloud-init clean --logs --seed` bootcmd, and a `scripts-per-boot` completion script), creates the chained overlay, then boots real QEMU and watches the serial console for a deterministic `sha256`-derived completion token (durably logged to `<output_dir>/<name>-boot.log`) with a monitor-socket graceful-shutdown timeout fallback. `tddy-vm-build` restructured to a `build`/`cloud-init` subcommand `Cli` (breaking CLI shape change — was a flat `--spec/--output/--format` invocation); `--base-image`/`TDDY_CLOUDINIT_BASE_IMAGE` is the only way to point at a base image (no bundled/auto-downloaded default, no machine-specific path baked in). `flake.nix` gains `xorriso`+`openssh`. Verified against multiple real QEMU boots in a nested-virtualization sandbox (not just skip-guarded): found and fixed a real bug (benign `set_hostname` module failure misclassified as fatal) and a real boot-speed fix (`-smbios type=1,serial=ds=nocloud;` to skip cloud-init's multi-datasource network crawl). The real-boot tests are production tests (`docs/dev/guides/testing.md` § Production Tests): `#[ignore]`d and additionally gated on `TDDY_CLOUDINIT_BASE_IMAGE` — they never run, even with `--ignored`, unless a developer explicitly supplies that env var.
