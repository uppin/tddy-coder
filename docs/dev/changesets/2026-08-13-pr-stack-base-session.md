# 2026-08-13 — **pr-stack-base-session

**Type:** Feature

a new orchestrator can be seeded from a session that already exists, and a planned PR can start its session in one step** — an operator holding a session on `feat/auth-store` had no way to say "the next PR stacks on top of this": a stack could only be populated by asking the agent to plan one from a description, by appending a *planned* node that owns no branch, or by adopting an existing **pull request** — which is exactly what a session that has not opened one yet does not have, so `adopt_pr_as_stack_node` is deliberately not extended. **tddy-service**: `StartSessionRequest.pr_stack_base_session_id = 31` and `AddPlannedPrResponse.node_id = 2`, both additive. **tddy-workflow-recipes**: `pr_stack::seed_stack_with_base_session` appends one root node bound to the base session's `branch`, name and id, leaving `branch_suggestion` and `pr_status` `None` (the node already owns a branch, and whether that branch has a PR is the live-status poll's to discover, not the form's to assert); the base-session half of its preconditions is factored into `check_stack_seed_base` → `SeededBase` / `StackSeedBaseRefusal` — an enum, so the daemon maps it onto a status code without re-deriving the rule — and the writer, `tddy-coder`'s startup gate and the daemon's pre-spawn validator now enforce one rule set in one wording where three prose variants used to drift; `read_stack` / `append_node_atomic` fold what had become the third copy of the append-with-`assign_missing_display_order` closure, since ordering is a stack invariant rather than each writer's business. **tddy-coder**: `--stack-seed-base-session <id>` plus a `StackPlanned` start state — forced, not preferred, because a seeded node owns a branch and `reseed_stack_from_plan_if_unspawned` would *reject* the `write-stack-plan` submit the planning phase would produce. **tddy-daemon**: `SpawnOptions` / `SpawnRequest` threading behind the extracted `spawner::pr_stack_spawn_args` (a flag silently not passed is this feature's failure mode, and an argument vector can be asserted on where a `Command` cannot), and `validate_stack_seed_base_session` refusing before anything spawns, so the form shows the reason instead of navigating to an orchestrator that came up unseeded. **tddy-web**: a "Base the stack on" picker gated on tool + `pr-stack` and scoped by the pure `stackBaseSessionCandidates` to branch-owning sessions in the form's own project and host that no other stack owns, and an "Add & start session" submit on the New-planned-PR form that opens the Start-session dialog for the node the *server* named. Three review defects, each pinned by a test watched failing against the defective line first: a refused seed still wrote `changeset.yaml` (so resuming it brought up an unseeded orchestrator nothing downstream can distinguish from a stack the agent has yet to plan), "Add & start" identified the added node by diffing the returned plan (the orchestrator agent appends to the same stack, so it could pre-fill and spawn against somebody else's branch), and nothing constrained the base session to the project's repository (the failure would have surfaced as a git error on the first descendant of an orchestrator that already looked seeded). Four further assertions were found vacuous only by mutating production behaviour and watching them stay green. Tests: five acceptance suites — 14 recipes, 19 daemon (two of them wiring tests driving the real `StartSession`, because every seam-level test passes with the proto field dropped on the floor), 9 coder, 13 + 8 Cypress — plus `stackParents` unit tests.
