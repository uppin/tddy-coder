# 2026-08-14 — the dashboard can see every LiveKit room, not just the one it joined

**Type:** Feature

`#/livekit` gains a second panel listing every room on the LiveKit server with the participants joined to each, so "is anybody actually in that room?" stops meaning shelling into the host to talk to the server API by hand; per-session terminal rooms, presenter rooms and screen-share rooms were previously invisible because the browser can only observe the room it is in. Fed by `ConnectionService.StreamLiveKitRooms`, snapshot-then-changes: the first message carries every room, each later message carries exactly one delta, so steady-state traffic tracks churn rather than roster size and an idle server produces an idle stream. The daemon polls LiveKit's server API every 3 s and diffs against the state it last sent **on that stream**, since a shared baseline would let one watcher's tick consume a delta another had not been sent yet; `livekit-api` was already a `tddy-livekit` dependency, so no new dependency enters the tree; this reads the same server API `RoomMetadataClient` writes session-room snapshots through. Participant metadata moved from a column to a card on hover **and keyboard focus** — reachable without a pointer, which also made it testable, since the component harness cannot synthesize the pointer events Radix listens for. Three defects the review found rather than the tests: the generated server-streaming pump discarded its send error and drained handlers into a void forever, so **every** subscription on **every** streaming RPC held its handler's "my subscriber left" check alive — with an idle-by-design feed that meant a permanent 3 s LiveKit poll leaked per visit (fixed in `tddy-codegen` for all three pump sites, plus a teardown watch in the poll loop, red-first proof: 32 reads vs 17); `useLiveKitRooms` never actually aborted on unmount, because a `cancelled` flag is only observed when the next event arrives and this feed is silent when idle; and an acceptance test that passed vacuously, its assertions already true of the pre-change DOM. Roster reads gained a 5 s deadline (a server that accepts and never answers left the panel on a stale roster looking healthy) and `MissedTickBehavior::Skip` (bursting missed ticks fires another `1 + rooms` calls exactly when the API is already slow). Feature [livekit-rooms-panel.md](../../ft/web/livekit-rooms-panel.md). Known and documented: poll cost is `1 + rooms` per **open subscription**, not per daemon, and with every agent session now holding a room of its own that count scales with session count — one shared poller broadcasting full rosters, each subscriber diffing locally, preserves the per-subscriber baseline at one poller per daemon and is the expected next change rather than a hypothetical escape hatch. (tddy-web, tddy-daemon, tddy-livekit, tddy-service, tddy-codegen)
