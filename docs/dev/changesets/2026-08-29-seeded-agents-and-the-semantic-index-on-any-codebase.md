# 2026-08-29 — seeded agents (and the semantic index) on any codebase placement

**Type:** Feature

selecting a specialized agent at session start was gated three ways: a peer-owned agent was refused on **every** start, *any* agent was refused on a **split** start, and the web withdrew the picker as soon as a codebase host was chosen. All three rested on one stated premise — that a peer is admitted to the session's room and given its clone only once the spawn opens that room — and the premise is false: `claim_agent_clone` opens the room itself. What was genuinely missing was **ordering**, because a spawn's `--allowedTools`/`--disallowedTools` are fixed at launch. A seed is now the same operation `AttachSessionAgent` is, performed before the spawn: resolve the placement, resolve each reference from the daemon that owns it, claim a clone for every agent **not** co-located with the authoritative worktree, then spawn with the withdrawn tool set derived from the roster just written — so a seeded agent's `replaces` is real at launch rather than at the next resume. Where an agent runs decides **how the session is split across hosts**, never whether it may be seeded; on a split placement the roster write is routed to the codebase host, so an agent owned by that host reads the authoritative worktree with no clone and an agent anywhere else gets one, exactly as an attach gives it one. A start that fails after a claim releases every clone (no entry, no half-built checkout, no room membership) — on the split path through `unwind_seeded_roster`, and on the three **co-located** launch paths through a `SeededCloneGuard` whose `Drop` releases unless `keep()` is called after the `.session.yaml` write, which is what let the co-located paths keep writing their roster inline *after* the spawn (they need the pid) while still claiming before it; the facts the claim needs are passed in (`SeedCodebase::of_a_starting_session`) rather than read back off a file that does not exist yet, which is what the earlier co-located refusal actually rested on. `semantic_index` is ungated on the same reasoning — it indexes a worktree, the worktree is on the codebase host, so that host builds it. `recipe` and `sandbox` stay refused on a split, each naming its field. The web drops both `!isSplitCodebase` guards and both submit-time blanks, so the request equals what the form shows. ⚠️ Behaviour change: `refuse_unenforceable_withdrawal` now runs on the co-located paths too — a seeded agent declaring `replaces` is refused on a shape where the withdrawal cannot be enforced (an unsandboxed cursor-cli start) instead of being accepted and silently unenforced. Known and unchanged: `SemanticSearch` still answers no query on any shape (query-side embedder unwired), `TDDY_SEMANTIC_INDEX_DB` does not yet reach a split session's exec-tool surface, a remote agent's `SHELL` still runs on the worktree host, and `recipe`/`sandbox` on a split remain out of scope.
