# 2026-08-30 — a sandboxed `workspace` session runs its tools inside a jail on the host holding the checkout

**Type:** Feature

`sandbox = true` meant one thing: spawn the *agent* in a jail. The tools it called still ran on the host, which is sound only while the jail and the checkout are on the same daemon. Move the codebase to another host — the placement [remote-managed-worktree.md](../../ft/daemon/remote-managed-worktree.md) exists for — and the thing the jail confines is no longer the thing that touches the repository, which is why `StartSession` refused `sandbox` together with `codebase_daemon_instance_id`: there was nothing on the codebase host for the flag to mean. The missing piece was a primitive rather than wiring, and it is this: `session_type: "workspace"` now takes `sandbox = true`, persists it, and gets a per-session jail at `<session_dir>/sandbox` holding the worktree read-write and nothing else of that host. `run_exec_tool_locally` turned out to be a single choke point — `ExecuteTool`, `StreamExecuteTool` and a roster agent's own loop all funnel through it — so one branch covers all three callers and none of them changed. The `SessionChannel` carried tool calls jail → host only, so `SessionFrame` gains `in_jail_tool_request`/`in_jail_tool_response` and `tddy-sandbox-runner` gains a `--workspace-tools` mode that runs the tool engine inside the jail and spawns no agent; the boundary enforced is the kernel's, not the tool engine's path checks. Three refusals make the no-fallback rule real rather than nominal: an unsupported platform is `failed_precondition`, a jail that will not provision unwinds the session rather than leaving one whose tools were never confined, and a session recorded as sandboxed whose jail this daemon does not hold — after a restart — is refused instead of served from the bare host. Two defects surfaced while building it, both fixed here and neither visible from a developer checkout: `./release`, `./install` and `publish.sh` never shipped `tddy-sandbox-runner`, which every jail spawns and which only a freshly installed host would miss; and every rendered Seatbelt profile granted the host's shared per-user temp base read **and** write, three separate ways, so a jailed `Shell` could read a host file outside its worktree on any stock macOS host — demonstrated by a confinement test that passed only because the dev shell sets an unusual `TMPDIR`. ⚠️ **Sandboxed `claude-cli` and `cursor-cli` sessions share that narrowed profile and are unverified end-to-end**: their four suites fail on this machine on a pre-existing `self_arc called before set_self_handle` panic, before any jail spawns; the rendered-profile delta for both recipes is exactly the removed rules and nothing else.
