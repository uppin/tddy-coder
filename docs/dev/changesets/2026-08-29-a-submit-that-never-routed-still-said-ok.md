# 2026-08-29 — a submit that never routed still said ok

**Type:** Bug Fix

a pr-stack planning session created its PRs only after recovering from two false green lights, and reading its transcript found three compounding defects. The `write-stack-plan` system prompt told the agent to submit "using the `submit` tool with key `stack-plan`"; no such tool is advertised, because `advertised_tools` deliberately excludes the CLI subcommands — so the agent searched every namespace for `submit` (`matches: []`), guessed `tddy-tools-approval_prompt`, took a `-32602`, and shelled out six discovery calls later. `run_submit` then read the routing goal **only** from the JSON body, defaulting to `unknown`, and used `--goal` solely to select a validation schema, so `--goal write-stack-plan` was discarded and the submission relayed to nobody; and `write-stack-plan` had no registered schema, so the wrong-shaped `{key, value}` payload was never validated. Together the last two returned `{"goal":"unknown","status":"ok"}` twice for two no-ops, which is why the agent spent the next ninety seconds reading `cli.rs`, `listener.rs` and `task.rs` to work out why nothing had happened. `resolve_submit_goal` makes `--goal` authoritative with the payload's `goal` as fallback; the goal is now resolved **once** and used for both validation and relay, closing the divergence that caused this. ⚠️ Behaviour change: a submission naming no goal in either place is a usage error (exit 2) rather than an `ok` under the goal `unknown`, as is a `--goal` contradicting the payload — deliberately scoped so the nine schema-less recipe goals (`assess`, `orchestrate`, `grill`, `interview`, `create-plan`, `prompting`, `reproduce`, `analyze-stack`, `evaluate`) keep submitting on `--goal` alone. `write-stack-plan` gains a proto, a schema (`urn:tddy:goal/write-stack-plan`; required `goal`, `version`, `prs`, each PR requiring `node_id` and `title`) and a `goals.json` entry, which must land together because `build.rs` hard-fails when the registry names a file that is not on disk. The prompt now spells out the `--data-stdin` heredoc as the tdd and bugfix prompts do, warns against building the JSON with `python`/`cat` (only `Bash(tddy-tools *)` is auto-approved), points at `get-schema`, names `$TDDY_SESSION_DIR` as where the artifacts land — the incident agent hunted the repository working tree — and drops the `stack-plan-md` submission, which nothing has ever consumed since `after_write_stack_plan` derives the markdown itself. The superseded `plan-pr-stack` recipe carried a second, divergent copy of both planning prompts with all the same defects; rather than fix the copy, both recipes now share one source in `plan_pr_stack/prompt.rs` parameterised by recipe name, which also ports the PR boundary contract across as that module's own note asked, and a test pins that the placeholder is substituted rather than shipped. Written test-first: 14 tests failed against the old behaviour, plus 3 more for the stale copy. Known and unchanged: the `createPlan` truncation and empty `planUri`, and the `switchMode` argument-casing mismatch, are Cursor-side and cost the same session another fifty-five seconds.
