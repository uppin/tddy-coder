# 2026-08-15 — **the bake path stopped lying about succeeding

**Type:** Fix

seven defects found by actually running it** — the chaining rework shipped with rendering tests green and every bake silently provisioning nothing. Running it end to end found seven, in the order each unmasked the next. **Three made a bake report success having done nothing:** the completion marker was written as a `scripts-per-boot` script, and cloud-init runs `scripts-per-boot` *before* `scripts-user`, so the guest halted before `runcmd` ever ran; `bootcmd`'s `cloud-init clean --logs --seed` deleted `/var/lib/cloud/instance/`, which is where cloud-init writes the `runcmd` script, so there was nothing left to execute (the reset now happens only immediately before a mid-bake `systemctl reboot`, where it is actually wanted — what re-provisions a copied base is the seed's fresh `instance-id`, not a reset); and the `users:` list replaced the image's default `debian` account, so `cc_ssh_authkey_fingerprints` died on `getpwnam` and failed `cloud-final` (the list now leads with the bare string `default`). **Four failed honestly, and were diagnosable because of the first three's fixes:** `$HOME` is unset in cloud-init's `runcmd` environment and the Nix installer refuses — *after* downloading its tarball, so it reads like a network fault; `.git` in a git **worktree** is a pointer file naming a host path, so `nix develop` resolved the flake as `git+file://` and chased it into nothing (`.git` is now excluded from the rsync, in the testkit *and* in `tddy_host.rs`, which had the same latent bug plus the same missing `HOME`); Nix's default HTTP concurrency makes QEMU's slirp drop connections part-way through a multi-gigabyte closure (`http-connections = 5`, longer stall timeouts, and a bounded retry that resumes from the store paths already fetched); and the per-VM login seed added days earlier re-declared the login account, letting cloud-init apply its default `lock_passwd: true` and locking the password the serial console depends on — two of this branch's own fixes colliding, invisible because the SSH path it was verified against still worked. Alongside: the guest now dumps `/var/log/cloud-init.log` and `/var/log/cloud-init-output.log` to the console between greppable markers and the host strips terminal escapes before writing its durable log, which is what turned the last four diagnoses from an afternoon into minutes; `run-vm-testkit --status` reports a layer as cached only when it is **sealed** `0444`, matching the code's own cache, rather than merely present. **Verified by real boots, not renders** — `bake_provisioning_acceptance` boots guests and asserts the provisioning landed in the sealed image, including a recipe that reboots mid-bake and resumes, and was itself proven to fail when the defect is reinstated. The full chain now bakes `tddy-nix-base` (1.2G delta — Nix and packages genuinely installed, against 21M when it provisioned nothing) and `tddy-builder` (9p kernel swap, reboot, warmed dev shell), boots the builder, and writes real `ELF 64-bit LSB pie executable, ARM aarch64` binaries back to the host. **Known blocker, recorded in `docs/dev/TODO.md`:** those binaries are linked against the dev shell's Nix glibc, so their ELF interpreter is a store path the test host does not have — `./install --systemd` completes and then `tddy-supervisor` fails `203/EXEC`. The five cgroups e2e tests are blocked on that, and the ELF-header assertion that passed them is too weak to have caught it. (tddy-vm, tddy-vm-testkit, tddy-vm-build, repo root)
