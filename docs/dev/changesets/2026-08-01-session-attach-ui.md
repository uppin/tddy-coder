# 2026-08-01 — **session-attach-ui

**Type:** Feature

documents can be attached when a session is created, staged to whichever daemon the browser is connected to and fetched by the host that runs the session, with the host reporting materialization progress over a streamed `StartSession`** — `8d9840f4` and `118e0441` had landed the whole host side of session attachments and **nothing called it**: `readHostDocument`, `HostDocumentRef`, `uploadStagedAttachmentChunk` and `context_docs` appeared in `packages/tddy-web` only inside generated code, so the only way to put a document in front of an agent was to start a session and then drop the file on its terminal — backwards, since the initial prompt that refers to the document is written in the create form. Building the client surfaced four host-side gaps and **two latent bugs**. **tddy-service**: streaming twins `StreamStartSession` / `StreamReadHostDocument` beside the untouched unary RPCs (so `tddy-tools`, `tddy-sandbox-app` and recipe hooks need no migration), `StartSessionEvent` / `AttachmentMaterializationProgress` / `HostDocumentChunk`, `HostDocumentScope.STAGED_ATTACHMENT`, `WorktreeDirEntry.size_bytes`, and two stale `NOT IMPLEMENTED` comment blocks deleted. **tddy-daemon**: the staging root moved to `std::env::temp_dir()/tddy-staging` (restart-cleared, retiring the abandoned-batch leak); a foreign-host staged ref is now **fetched** rather than refused, through the new scope — the `.staged-complete` marker checked on the *owning* host is what actually prevents a truncated attachment, so requiring same-host had been the blunter way of getting the same property; `forward_server_stream_to_peer` relays peer frames into `MpscResultStream<T>` with a per-frame idle deadline; `start_session`'s body extracted verbatim into `start_session_core(req, progress)` with a discarding sink on the unary path; `max_attachment_bytes` config key enforced host-side and advertised in the common room. **Bug 1:** `forward_to_peer` addressed a peer by its **bare** instance id while a daemon serves RPC on `daemon-{instance_id}` — the bare identity is the discovery participant, which runs no `ServerEngine` — and with no deadline the symptom was a call that never returned and never errored; every fixture peer in the repo had served under the bare id, which is precisely what hid it, and four fixtures were rewired to the production arrangement. **Bug 2:** a cross-host staged attachment was silently capped at 4 MiB by the unary forwarded read while the same file staged locally had none, so a large document attached on one host and failed across two. **tddy-web**: an attachments section on `CreateSessionPane` for every session type and in peer mode — picker, drag-drop, editable basenames, per-row streamed progress, and a `HostDocumentPicker` over all four scopes reusing `WorktreeFileTree`; staging happens on submit and is memoized per row (keyed on `File` identity **and** staging host) so a branch-conflict retry re-uploads nothing; `streamStartSession` only when attachments are present; the stream consumed with a `cancelled` flag, never `AbortController`, because the LiveKit transport accepts and ignores `_signal` for server-streaming and a spec using it would pass while the real stream ran on; basenames compared case-insensitively because the host's `create_new(true)` makes a `Spec.md`/`spec.md` pair fail the whole `StartSession` on macOS. Tests: daemon `session_attach_cross_host_acceptance` 8 (two daemons over the LiveKit testkit, including a 4.5 MiB transfer crossing hosts *inside* a forwarded stream), `session_attach_staging_scope_acceptance` 11, `staged_attachment_path_validation` 8, `daemon_advertisement_attachment_cap` 4, `staging_rpc_acceptance` 7, `worktree_files_rpc` 8, `--lib` 424; web 24 attachment/picker Cypress + 90 across the existing `CreateSession*` specs + 563 bun units; `clippy -D warnings`, `cargo fmt --check` and `bun run build` clean. **Known limitation:** nothing has been exercised against a real daemon from a browser — the daemon suites drive `ConnectionServiceImpl` directly and every Cypress spec stubs the RPCs — so a manual two-daemon `./web-dev` verification is outstanding, with the steps recorded in [TODO.md](../TODO.md) alongside ten follow-ups.
