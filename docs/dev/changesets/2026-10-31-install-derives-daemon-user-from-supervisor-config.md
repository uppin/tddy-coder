# 2026-10-31 — Install derives the daemon user from supervisor.yaml

**Type:** Bug Fix · **Packages:** root `install` script, tddy-e2e (tests), daemon product docs

`./install` held a second source of truth for the daemon's OS account: `INSTALL_DAEMON_USER`/`INSTALL_DAEMON_GROUP` were rendered into `supervisor.yaml` once and then kept driving account creation and the log/auth `chown -R` on every later run, independent of the `user:`/`group:` the preserved config declares. A host whose operator changed either side ended up with the supervisor spawning the daemon as one account against directories owned by another — crash-looping on bare `Permission denied`, unrecoverable by restart because nothing in the runtime re-chowns.

State B: on an upgrade install reads the `tddy-daemon` service's `user:`/`group:` back from the preserved `supervisor.yaml` (indentation-aware extraction scoped to the service block, so the `socket:` block's own keys are never mistaken for the identity) and derives all account work from it. The env vars seed only a fresh install's rendered config; disagreement is a hard error naming both values; a config without a usable `user:`/`group:` is refused with the remedy (no fallback); a config-declared `root` is refused naming the config. Seven new e2e tests in `packages/tddy-e2e/tests/install_supervisor.rs` cover the decision paths rootlessly; the real `useradd`/`chown` stays covered by the VM image chain with the default identity (accepted gap — deriving a different user in a VM bake costs an hours-long re-bake).
