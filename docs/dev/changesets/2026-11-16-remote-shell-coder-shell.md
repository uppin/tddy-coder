# 2026-11-16 — Coder workspaces as a remote-shell transport

**Type:** Feature · `#remote-shell` 4/7, PR [#918](https://github.com/uppin/tddy-coder/pull/918), base `feature/remote-shell/ssh-agent-launch`, wave 2 of 4

A Coder workspace becomes the second transport of the remote-shell port, driven by the `coder` CLI on the daemon's host with the account's URL and token. The daemon also lists the workspaces a Coder account can reach, with their status.

## What changed

- **tddy-remote-shell**: `src/coder.rs`: `CoderShell::new(credentials, workspace)` / `::through(coder_binary, …)`; `CoderCredentials { url, token: SecretString }`; `CoderWorkspaceRef { owner, name, agent: Option<String> }`. See [architecture.md](../../packages/tddy-remote-shell/docs/architecture.md).
- **tddy-service**: `proto/host.proto`: `rpc ListCoderWorkspaces`, `CoderWorkspace`, `HostCoderCli` on the tooling response; TypeScript regenerated in both gen directories.
- **tddy-host-service**: `src/coder_workspaces.rs`: `trait CoderCredentialSource`, `trait CoderWorkspaceSource`; the handler in `src/service/coder_workspaces.rs`; `CoderCliStatus` / `classify_coder_version` in the tooling probe.
- **tddy-daemon**: `HttpCoderWorkspaceSource` (HTTP listing beside the daemon's client), `VaultCoderCredentialSource` over `CoderAccounts::credentials_for`, wired by `coder_credential_source::wire_coder`; `CODER_URL` / `CODER_SESSION_TOKEN` scrubbed from probes run as another user.
