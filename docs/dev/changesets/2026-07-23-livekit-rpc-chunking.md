# 2026-07-23 — **livekit-rpc-chunking

**Type:** Feature

wire the chunking codec into the LiveKit RPC transport (Rust + web)** — oversized LiveKit data-channel messages (>64,000-byte negotiated SCTP max) were rejected on `publish_data` and retried 30× forever by `SharedPublisher`, wedging production `tddy-daemon` and starving small RPCs like `ListSessions` (the web dashboard saw `premature EOF` / `cant skip wire type 4` protobuf decode errors and appeared stuck). PR #322 shipped `packages/tddy-livekit/src/chunking.rs` as a tested but **unwired** module; this changeset wires it end-to-end. Send paths (`client.rs::publish_request`, both `participant.rs` response drains, and the TS `transport.ts::publishRequest`) frame via `frame_for_transport`/`frameForTransport`; receive paths reassemble **per sender** (`client.rs`, `client_factory.rs`, `participant.rs`, and the TS `RoomRpcRegistry` / standalone `LiveKitTransport`) — message ids are unique only within one sender, and a browser talks to several daemons on one room. Back-compat: a payload that fits one packet is sent raw (byte-for-byte); only oversized ones split, each chunk frame prefixed with a `0x00` magic byte a valid prost `RpcRequest`/`RpcResponse` can never begin with (protobuf field 0 is illegal; the envelopes' lowest fields are 1/2), so peers disambiguate raw vs chunk on the first byte. `packages/tddy-livekit-web/src/chunking.ts` mirrors the Rust codec byte-for-byte. Verified: Rust 25 lib + TS 26 pkg unit tests, clippy clean, `tddy-daemon` builds, and a real-LiveKit `rpc_scenarios` round-trip of a 370 KB oversized echo in both directions. Follow-up (deferred, separately tracked): cap `result_json`/`input_json` at the activity-log layer (`tddy-daemon/src/tool_call_log.rs`) so records stay small regardless of transport; a Cypress e2e crossing the TS↔Rust boundary is also outstanding.
