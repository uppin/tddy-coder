# 2026-10-31 — The supervisor config owns the daemon's OS identity

- `./install --systemd` no longer keeps a second source of truth for the daemon's OS account: on an upgrade it **reads the `tddy-daemon` service's `user:`/`group:` back from the preserved `supervisor.yaml`** and creates the account, adds it to the socket-access group and chowns the log + auth directories to *that* identity. `INSTALL_DAEMON_USER`/`INSTALL_DAEMON_GROUP` only seed a freshly rendered config; an env var that disagrees with an existing config is an error naming both values, never a silent winner.
- A `supervisor.yaml` whose `tddy-daemon` service lacks a usable `user:` or `group:` is refused with the remedy — there is no fallback to a default the operator never declared. A config declaring `root` is refused with a message naming the config as the source (previously only the env var was checked).
- Background: an operator who changed the config's user (or re-chowned the log/auth directories by hand) got a daemon spawned as one account against directories owned by another — crash-looping on bare `Permission denied` on its log files and signing key, unrecoverable by a restart because nothing in the runtime ever re-chowns. `daemon.yaml` cannot own the uid (the spawning parent chooses the user before the daemon process exists), so `supervisor.yaml` — already the host's privilege surface — is the single source. See [systemd-install.md](../systemd-install.md).
